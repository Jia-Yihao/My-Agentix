## 2. P0 · 先纠正一处**误诊**（不改这处，后面所有跑批都会产出错报告）

`evals/README.md:833` 此前记的是：「录制侧把 `perf.llm_steps` / `perf.llm_latency_ms` 写成了**常量 0**」——本轮按代码复核改准，§10.5 与 `CHANGELOG.md` 对应条目已改为下方三层口径。
本轮沿代码读到的是**三层不同的问题**，没有一层是"写死一个 0"：

1. **生产路径只有一个步骤**。整条 ask 被包成一次 Runtime 步骤，类型是 `EXECUTING`
   （`agentix/application/services/chat_service.py:869`–`870`，`runtime.astep(StepType.EXECUTING, "agent_graph", …)`；
   `agentix/runtime/runtime.py:185` / `:199` 同样只用 `StepType.EXECUTING`）。
   `agentix/` 里除这三处 `astep(` 调用点外再无登记步骤的地方（grep 实测），所以轨迹里根本没有 LLM 粒度的步骤。
2. **词汇表里有 `GENERATE = "generate"`，但没人用它**（`agentix/domain/runtime/steps.py:21`–`31` 定义 ROUTE / PLAN / TOOL / RETRIEVE / VERIFY / GENERATE / GUARDRAIL / EXECUTING，其中 `GENERATE` 在 `steps.py:29`；grep `StepType.LLM` / `StepType.MODEL` / `StepType.GENERATE` = **0 命中**）。
3. **报告侧的判据只认带 `llm` 字样的类型**（`evals/run_eval.py:656`–`658`：`if "llm" not in step_type: continue`）⇒ 就算第 2 条补上了 `generate`，这里照样不计。

**后果的形态也不同**：`run_eval.py:644`–`648` 在 `steps` 不是列表时**只返回 `latency_ms`、不留 `llm_steps` 键**（这是纪律：缺就说缺，不补 0）；而冒烟预测档里 `llm_steps: 0` 与 `llm_latency_ms: 0.0` 是**存在的**（`.tmp/smoke_preds.jsonl` 三行皆然）⇒ 说明 steps 列表取到了、只是**里面没有一条算 LLM 步**。这是"真的没采到"，不是"填了个 0"——两者的修法完全不同：前者要在执行链里补步骤登记，后者只要删一行常量。

**P0 的验收**（不跑模型，纯只读对账）：`evals/README.md` §10.5 与 `CHANGELOG.md` 里那条"常量 0"的措辞改成上面三层，并各带一个 `文件:行`。

**状态：已闭合**（同日）——§10.5 与 `CHANGELOG.md` 两处均已按上述三层改准并各带 `文件:行`；`evals/README.md:833`–`843` 与本文件 §2 同口径。P1–P4 **未开工**，本文件仍是规划不是完成记录。

**工时**：一处文档措辞（半小时）。**风险**：无（不动代码）。

## 4. P2 · 路由口径：把"0 分"读成它真正的意思

冒烟实测读数（`evals/README.md` §10.5 / `.tmp/smoke_report.md`）：3 题的 `route_type` 分别是
`kb-query` 与 `text2sql-query`（金标 `route_type` 恒为 `general-query`），**路由准确率 0**；
**三题（两条管线）都被**各自领域的 guardrails 拒答，于是**回复里没有选项字母** ⇒ 报告写
「0/0 可判分；抽不出字母 3 题」。

这条链要读对：**"抽不出字母"不是一个独立缺陷，它是路由错了之后的下游结果。**
把它列成两项会让下一次改动去修错的地方（给提示词加"请回答字母"），而真正的缺口是
**通用问答在路由层被领域出口抢走**。两种口径必须分清：

- **口径 A（改评测集）**：金标 `route_type` 允许一个**可接受出口集合**（例如 `general-query` 或
  `kb-query` 都算对）。成本低，但会把"系统其实答对了"和"系统答对了但走错了门"混成一个数——
  **不推荐**，评测集的意义就在于它能指出这条分歧。
- **口径 B（改系统，推荐）**：保留单一期望出口，把"MCQ 直答题被路由进领域出口"当成一个**真实缺陷**
  去收敛。可用既有兜底计数器 `router_fallback_total{reason}` 那条线（见 `CHANGELOG.md` 关于 §24.2 的条目）
  先量化"156 题里有多少题进了哪个出口"，再决定是加"含选项列表的直答题优先 general-query"这类判据，
  还是补 L1 的 few-shot 边界。

⚠️ 无论选哪种：**`code-query` 不进评测词汇表**（`evals/run_eval.py:115` 的
`ALLOWED_ROUTE_TYPES` 与 `/routes` 端点都保持 7 类；行号随实现漂移，原引 `:102` 为 2026-10-26 建档值，2026-10-27 实测现值 `:115`，复现命令：`grep -n "ALLOWED_ROUTE_TYPES" evals/run_eval.py`），这条是 2026-10-26 已经定下的裁决，
不要顺手扩到 8。

**工时**：口径 B 的量测部分约 0.5 天（跑批本身见 P4 的成本）；改判据属架构改动，需要维护者先定方向。

## 5. P3 · 一份"活的报告"最小可交付（这是叙事缺口的真正补齐点）

外部意见要的"哪怕 10 条跑通一次"在本仓库有现成的机器，成本可测：

| 档 | 题数 × 臂 | 单题实测 | 预计墙钟 | 产出 |
| --- | --- | --- | --- | --- |
| 冒烟（已做过） | 3 × 1（扁平） | 29.3s / 40.5s / 45.5s（`.tmp/smoke_report.md`：p50 4.045e+04 ms、最大 4.553e+04 ms，n=3） | 约 2 分钟 | 已登记在 §10.5，**不算成套报告** |
| 最小可交付 | 10 × 1（扁平） | 同上量级 | **7–8 分钟** | 一份 `mcq_report.py` 的 markdown，落 `.tmp/`（**不入库**，入库属基线变更，纪律 5） |
| 成套单臂 | 156 × 1 | 同上 | 约 1.8–2 小时 | 可展示的正确率 + 延迟分布 + 出口契约 |
| A/B 双臂 | 156 × 2（多 agent 开 / 关） | 同上 | **3.5–5 小时**（两臂**必须串行**：LM Studio 单实例并行会把延迟读数污染成不可比） | 多 agent vs 扁平的同题对照，才是"量化多 agent 性能"这句话的证据 |

**硬前置**：P1（否则报告里"每题 LLM 步数"这项恒 0，等于交出一份自相矛盾的报告）；
P2 至少要先做完"量测路由分布"那半段（否则正确率会是 0/0 可判分，报告没有可读的结论）。

**当前裁决**：维护者 2026-10-26 明确「**本轮不跑评测**」，本文件**不把它排进本轮**。
上表存在的意义是：当裁决放开时，跑哪一档、多久、必须先有什么，已经算好了。
