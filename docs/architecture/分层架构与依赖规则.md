# 分层架构与依赖规则

本文档定义 My Agentix 的代码分层、各层职责、**依赖方向规则**及其自动化守卫。
任何 PR 违反规则都会被 CI 拦下，请在编码前通读。

---

## 1. 分层总览

```
┌─────────────────────────────────────────────────────────────┐
│  interfaces/            接口层（协议转换）                     │
│  HTTP 路由、请求/响应模型、中间件                               │
└───────────────────────────┬─────────────────────────────────┘
                            │ 调用（允许）
┌───────────────────────────▼─────────────────────────────────┐
│  application/           应用层（编排与业务规则）                │
│  Agent 图、服务（会话/记忆/观测/任务）                          │
└───────────┬───────────────────────────────┬─────────────────┘
            │ 依赖抽象（允许）               │ 实现注入（运行时）
┌───────────▼───────────────┐   ┌───────────▼─────────────────┐
│  domain/                  │   │  infrastructure/            │
│  领域层（零外部依赖）       │◄──┤  基础设施层（实现 ports）     │
│  错误 / 策略 / 端口 / 状态  │实现│  LLM / 向量库 / 图库 / 持久化 │
└───────────────────────────┘   └─────────────────────────────┘
```

**核心思想**：`application` 依赖 `domain` 定义的**抽象**（Protocol），
`infrastructure` **实现**这些抽象。依赖箭头最终指向 `domain`，而非具体实现。

**终态顶层包归属**（统一执行链 Stage M 后，M6 收口）：

| 顶层包 | 层次归属 | 依赖方向 |
|---|---|---|
| `interfaces/` | 接口层 | → application / domain |
| `application/` | 应用层（用例编排） | → domain / orchestration / policies / tools |
| `orchestration/` | 编排层（AgentLoop、LangGraph 图结构、多智能体策略） | → domain（纯编排，不 import LangGraph 之外的上层） |
| `policies/` | 横切策略执行件（Planner / Verifier / HITL / Guardrails） | → domain |
| `tools/` | 工具层（注册面 / gateway 执行闸 / adapters） | → domain / policies（经 gateway） |
| `agent/` | Context Provider 家（context / memory / events / hooks / skills / evolution） | → domain only |
| `runtime/` | Agent Runtime（步骤 / 预算 / 生命周期 / 控制平面） | → runtime / domain（运行期自包含） |
| `capabilities/` | 能力层（mcp/） | → tools / domain |
| `retrieval/` | 检索域垂直切片（自带 api / domain / infra / usecases） | 域内自治（澄清：域内自治指**不承接上层反向依赖**；其自身出边是否放行以本表「依赖方向」列为准，M1 按最保守字面取**空集**，`retrieval → domain` 目前仍登记为违例、不放宽） |
| `infrastructure/` | 基础设施层（实现 ports） | → domain |
| `observability/` `reliability/` `security/` `crawler/` | 横切支撑 | → domain / config |

## 2. 各层职责

### 2.1 `interfaces/` — 接口层

**职责**：协议转换与鉴权。把 HTTP 请求翻译成应用层调用，把结果翻译成响应。

| 允许 | 禁止 |
|------|------|
| 参数校验、请求/响应模型定义 | ❌ 业务编排（多步骤流程） |
| 调用 application 服务 | ❌ 直接操作 ORM / 数据库会话 |
| 错误 → HTTP 状态码映射 | ❌ 直接调用 `infrastructure` 具体实现 |
| 中间件（trace / 鉴权 / 日志） | ❌ 包含检索/推理逻辑 |

**代表文件**：`interfaces/http/v1/chat.py`（322 行，仅做「校验 → 调服务 → 组装响应」）、
`interfaces/http/v1/upload.py`、`interfaces/http/models/*.py`。

> 反例（已修复）：历史上 `chat.py` 曾在路由函数内建会话、写 `chat_message` CRUD、
> 编排落库与响应组装（653 行）。这违反规则 1，已下沉到 `ChatService`。

### 2.2 `application/` — 应用层

**职责**：编排领域能力完成用例。持有 LangGraph 图、服务编排、事务边界。

| 允许 | 禁止 |
|------|------|
| 编排 domain 端口 / 策略 | ❌ 直接 import `infrastructure` 具体实现 |
| 定义 Agent 图与节点 | ❌ import `interfaces`（HTTP 契约） |
| 通过注入获取仓储 / 图 / LLM | ❌ 在模块顶层 new 基础设施客户端 |

**代表文件**：`application/services/chat_service.py`、
`application/agents/kg_sub_graph/**`、`application/services/observability.py`。
（图结构 `orchestration/langgraph/lg_builder.py` 归编排层，见 §1「终态顶层包归属」。）

> **注入模式**：`ChatService.__init__` 接收 `SessionRepositoryPort` / `MessageRepositoryPort`
> （`domain.ports` 的 Protocol）与 `graph_getter`（`GraphProviderPort`）。
> 默认实现由 `infrastructure.persistence.repositories` 提供，但类型标注面向抽象。

### 2.3 `domain/` — 领域层

**职责**：表达领域概念与规则。**零外部依赖**（仅 stdlib + typing）。

| 子包 | 内容 |
|------|------|
| `errors.py` | 错误**词汇表**：`ErrorCode` 枚举、`DEGRADABLE`、`HTTP_FATAL`、`AgentError` |
| `status.py` | 响应状态枚举 `RequestStatus`（ok / degraded / error） |
| `tracing.py` | `trace_id` 的 ContextVar 与读写函数 |
| `agent/` `runtime/` `tool/` | Agent / Runtime / Tool 的**领域类型与端口**（M0 拆分，纯契约） |
| `policies/` | 判定**函数**：`is_retryable`、`aretry`、冲突裁决 |
| `ports/` | 抽象接口（`Protocol`）+ `Payload` TypedDict |

> **词汇表 vs 策略**的分区：`errors.py` 回答「有哪些错、属哪一类」；
> `policies/` 回答「遇到这类错该怎么做」。

### 2.4 `infrastructure/` — 基础设施层

**职责**：实现 `domain.ports` 定义的抽象，封装外部系统。

| 子包 | 内容 |
|------|------|
| `llm/` | LLM 调用加固（`retry.py`，re-export `domain.policies.retry`） |
| `persistence/` | 数据库引擎、CRUD、**仓储实现**、Redis Checkpointer |
| `text2sql/` | Wren 文本转 SQL 适配器 |
| `core/` | 日志、安全、限流 |

> 原 `knowledge/`（向量库 / Reranker / Embedding）已归检索域 `agentix/retrieval/infra/`；
> 原 `tools/`（ToolRegistry / ToolSpec）已随 M1/M6 迁至顶层 `agentix/tools/`。

| 允许 | 禁止 |
|------|------|
| 实现 `domain.ports` 的 Protocol | ❌ import `interfaces` |
| import `domain`（实现契约所需） | ❌ 反向依赖 application 的业务逻辑 |

### 本地运行守卫

```bash

```

### 守卫的「棘轮」语义

规则 2 的守卫使用 **集合相等断言**（`==`，非 `issubset`）：

- 出现**新**违规 → 失败（挡住新债）
- 已登记违规**被修复** → 也失败（逼迫收紧白名单常量，防止白名单长期残留）

当前 `application → interfaces` 的白名单为**空集**（零容忍，P2-6 完成后达成）。

## 7. 规则的可执行化（M1–M3）

§1 的「终态顶层包归属」是**设计意图**，§3 的 R1–R4 是**已执行的窄规则**。两者之间的差距可以量出来：本节记录 2026-10-28 的全矩阵实测结果，以及把意图表变成断言的三项工作。

### 7.1 实测拓扑：规则只覆盖了四条边

口径：对 `agentix/` 下全部 `.py` 做 AST 扫描，只取 `agentix.<包>` 形式的绝对导入（相对导入必然同包，不计），按「源包 → 目标包」聚合，计 import 语句数。`agentix/` 顶层共 17 个包。

结果：**12 个包落在同一个强连通分量里**——`agent`、`application`、`infrastructure`、`observability`、`orchestration`、`performance`、`policies`、`reliability`、`retrieval`、`runtime`、`security`、`tools`。它们之间不是单向箭头，而是环。（**系 2026-10-28 M2 拆边前快照，历史值**：M1 闭包矩阵最新实测同一强连通分量为 **8** 个包——现行值见本节末「实测快照」块；原句保留为留痕，不冒充现行断言。）

零出边的只有三个：`config`、`crawler`、`domain`。这三个才是 §1 所说「不知道外面世界」的底层。

### 7.2 三条外来设计原则的取用

来源是 pi-agent 的包组织实践，逐条对照本仓：

| 原则 | 判定 | 理由 |
|---|---|---|
| **依赖漏斗**：先画依赖箭头，底层不知道外面世界、顶层知道一切 | **不引入，本仓已有更细的版本** | §1 已有分层总览、逐包归属表、各层允许/禁止表与归属决策树，粒度比「三层」更细。缺的是 7.1 记录的执行面，不是设计 |
| **类型递进扩展**：底层定义原子类型，上层用继承与联合类型扩展、不改底层 | **只在原则层采纳，不重构类型体系** | Python 单包没有包间 `extends`；「底层可独立发布复用」的收益在本仓不存在——对外发行的是 `agentix` 一个包，没有「只装 domain」的消费者。`domain` 已有 13 个 `Protocol` 与 8 个 `TypedDict`，原子类型层已经成立。真实缺口在别处：README 的测试基线只记录 `mypy` 对 `agentix/domain` 的结果，上层扩展类型没有静态检查——落点是扩大类型检查覆盖面，不是重建类型树 |
| **可独立使用测试**：移除上层依赖，看底层还能不能编译通过 | **采纳，但实现必须换** | `package.json` 删依赖的验证方式在 Python 单包下不成立（一个 `pyproject.toml`、一个发行单元，「上层」删不掉）。等价物是**导入闭包断言**：对每个顶层包静态计算传递依赖闭包，断言闭包不含归属表禁止的层。它比 npm 版多抓一类问题——间接越界（A import B、B import C，则 A 的闭包里有 C） |

### 7.3 M1：把归属表变成断言

三步与第 4 步的两条守卫口径**均已落地**（2026-10-29，登记为已完成；落点全部是 `tests/test_p177_arch_closure.py` 的六条守卫，对应关系：第 1 步的机器可读允许集 = `ALLOWED`、第 2 步的闭包计算器 = `_transitive_closure`、第 3 步的相等棘轮 = 守卫 #1 与守卫 #3、第 4 步的「每条例外必须写理由」= 守卫 #2 与「登记不许腐化」= 守卫 #1/#3 的双向相等——已登记而实际消失的边同样红）；下面的「三步」与第 4 条是修法的设计理由原文，一字未改，不作待办声称。

三步：

1. 把 §1 表「依赖方向」一列写成机器可读的允许集（包 → 允许依赖的包集合），作为 `tests/` 侧常量，不进 runtime。
2. 写闭包计算器：对每个顶层包，沿 `agentix.<包>` 绝对导入做传递闭包，得到「实际触达的包集合」。
3. 断言 `实际闭包 ⊆ 允许集`。过渡期用棘轮语义——沿用 R2 那套「集合相等断言」：先录基线，再只许减少。

为什么用闭包而不是逐边检查：逐边检查时，`tools → application` 这类两条边很容易被写进白名单后永久合法；闭包会同时暴露 `tools → application → 其余全部` 的传递后果，白名单没法悄悄变宽。

4. 两条守卫口径，缺了 M1 会慢慢失效：
   - **每条例外必须写理由**：允许集里每一条「包 → 包」都带一句为什么允许（写进常量旁的结构化字段，不是注释），没有理由的例外不许合并。
   - **登记不许腐化**：允许集里列出、但实际已经不存在的边，断言必须红，提醒把它删掉。否则白名单只增不减，守卫等于在放水。

   这两条不是自创。同类守卫里成熟的版本是把规则外置成一份 yaml、断言写成测试，再加「每条 exceptions 必须写理由」与「known_deviations 必须仍然成立」两条——后者是唯一能防住「例外一登记就永远躺着」的手段。本项目的 M1 若不补这两条，基线会缓慢腐化：棘轮只保证「不变宽」，保证不了「该收的没收」。

### 7.4 M2：拆三条最便宜的反向边

三条边的修法**均已落地**（2026-10，登记为已完成；「现状」列写落地后的真话）：

| 边 | 现状（已落地后） | 修法（登记） | 依据 |
|---|---|---|---|
| `observability → retrieval` | 已拆：`TRAJECTORY_DIR`、`LOG_JSON_ENABLED`、`LOG_LEVEL` 真源上提 `agentix/config/settings.py`（env **值**语义逐位复刻旧实现：`_bool_env` 的 `1/true/yes` 判据经 `field_validator(mode="before")` 保留、`LOG_LEVEL` 无条件 `.upper()` 保留、`TRAJECTORY_DIR` 默认路径与原检索域 `_BASE_DIR` 上溯三级同源；**`.env` 文件基准随真源迁移变为工作目录口径**——旧实现在仓库根绝对路径 `load_dotenv` 之后导入期现算，新实现由统一 Settings 按 `env_file=".env"`（CWD 相对）解析，工作目录 ≠ 仓库根时存在两个方向的差异：stray CWD `.env` 会被读到、仓库根 `.env` 的值会丢回落默认，已按台账 M2-1 行登记偏离），`logging_config.py` / `trajectory.py` 直读 config；`agentix/observability/` 对 `agentix.retrieval` 的 import 为 0 | 已完成 | 与 ADR-0003「配置声明单一事实来源」一致；该文件 docstring 自述只是「兼容包装」 |
| `tools → application` | 已拆：纯作用域类型（`RequestScope` / `_scope_var` / `get_current_scope`）下沉 `agentix/domain/request_scope.py`（纯 stdlib），写入实现与导入期注册留 application（再导出保持对象同一），`tools/gateway/executor.py` 改指 domain。KG 工具 4 个参数模型的规范位落 `agentix/tools/kg_arg_schemas.py`（tools 层），`kg_tools_list.py` 为再导出 shim | 已完成 | §4 已为 `trace_id` 定过同一归属：纯 ContextVar 放 `domain`。KG schema **落 tools 而非 domain**：`tests/test_p17_domain_layer.py` 对 domain 零豁免第三方依赖（pydantic 模型进 domain 必红），且参数 schema 属工具契约数据，与 `ToolSpec` 同层 |
| `runtime → application` | 已拆：预算结构 `DEFAULT_WARN_RATIO` / `BudgetVerdict` / `TokenBudget` 下沉 `agentix/domain/runtime/token_budget.py`（纯 stdlib，`to_dict()` 键序不变），`BudgetLedger` 与 ContextVar 台账读写留 application；`runtime/control_plane.py` 的 TYPE_CHECKING 引用改指 domain | 已完成 | 同上：预算数据结构下沉 `domain`，读写实现留在 application；§1 给 `runtime` 的定义是「运行期自包含」 |

三条都不改行为，只改归属与 import 源，可各自独立成批。

### 7.5 M3：编排层去具体化

`orchestration → application` 的 27 条是全仓最大的反向依赖，集中在 `agentix/orchestration/langgraph/lg_builder.py` 与 `agentix/orchestration/langgraph/lg_supervisor.py`：建图与分派时需要 10 个具体 handler（router、guardrails、image / file / code / task / general handler、LLM 工厂、multi_tool 工作流、legal retriever）。

已核实这些符号在文件内确有调用——部分 import 带着 `# noqa: F401`，但那是历史注释，实际并非纯 re-export，所以不能靠删导入解决。

修法，对齐「core 不知道具体 agent、只接收注入」：
1. 在 `orchestration` 侧定义节点注册协议（`register(name, factory)` / `get(name)`）。
2. `application` 在装配期注册全部 handler。
3. 两个文件只接收注册表，不再顶层 import 具体 handler。

风险最高：改的是建图入口，回归面覆盖全链路。必须最后做、单独成批。

### 7.6 边界

- 不重排顶层包、不改 §1 的分层设计、不引入 import-linter——闭包断言用 AST 即可，与 `tests/test_p66_arch_guards.py` 里已有的扫描器同源，不新增依赖。
- M3 若评估后判定回归成本高于收益，允许只做 M1 + M2，把 M3 留作已知债——但**必须登记进 §5**，不能停留在「文档写了终态、代码是环」的状态。
- **M4（Agent 内核、工具管道与上下文）不属于本节的依赖拓扑范围**，方案与排期见 `docs/design/性能与优化路线图.md` §8。本节对它唯一的约束是**落位**：`StopReason` 属 `domain` 的值对象；接缝与工具输出上限（M4-f，改的就是 `_invoke_tool_call`）留在 `retrieval/usecases/` 的 runner 内；压缩的增量更新（M4-g）留在 `agentix/agent/context/`，而 `agent` 包当前对 `application` 只有 1 条边，这项改动不许把它变成 2 条。M1 的闭包断言对这些落位照常检查；因为那个循环不在 LangGraph 里，本节 §7.1 的边矩阵不覆盖它。
