# ADR-0007: 工具执行位置做成可声明的端口（ExecutionSandbox）

- 状态：已采纳（⑭ 端口 + `in_process`/`thread` 两档 + ⑮ `subprocess` 档 + ⑯ 能力探测**已实现**；
  ⑮ 于 2026-10-25 落地，`TOOL_SANDBOX_SUBPROCESS_ENABLED` 默认关。
  **仍未收口**：`container` 档、只读根与指定可写目录、出网默认拒绝——那三件属 ⑰/T3。
  **[补记 2026-10-26]** 原列在此处的 `RLIMIT_NPROC`（进程数闸）已实现，是 ⑰ 四件里唯一买到的一件，
  也是唯一**带前置**的一道闸：只在 `TOOL_SANDBOX_SUBPROCESS_UID` 配了**独立且非 0** 的 uid 时落下，
  上限 32 个**任务**（内核按任务计费，线程也算；容器里可见的进程/任务计数只是下限））
- 日期：2026-10-23
- 相关：[ADR-0001](0001-分层架构与端口抽象.md)（分层 + 端口）、
  [ADR-0006](0006-基础设施关键性与降级.md)（依赖关键性）、
  [PROJECT_SPEC §24](../../项目实现手册.md)、[runtime-guardrails §15](../运行时护栏.md)、

## Context（背景）

统一 `ToolExecutor`（`agentix/tools/gateway/executor.py`）管住了**要不要执行**
（有效风险 → 权限 → 人工审批 → 护栏），也管住了**执行多久**（`timeout_ms` + 重试 + 舱壁），
但从没管过**在哪儿执行**：所有 handler 都在 backend 那个进程里被 await。于是：

1. 一个 handler 崩出进程边界的能力 = 零。它抛异常会被 `execute` 吞成 `ToolResult`，
   但 `os.environ`、文件权限、`ulimit`、宿主 namespace 与主进程**完全共享**。
   §24.2 的结论因此是「闸门严、边界有了一格、但仍然没有墙」。
2. 唯一一次"下放线程"（§24.2 G1，`TOOL_SYNC_OFFLOAD_ENABLED`）是**全局 flag**：
   为了让一条同步 handler 的超时能截断，要改变**整个实例**所有 handler 的循环亲和语义。
   这不是隔离，是一刀切的副作用交换——而且「哪条工具需要下放」这件事在代码里不可声明、
   不可 grep、不可测。
3. 真正走出去的那条路径（MCP stdio 子进程）证明边界是会漏的：子进程默认继承主进程
   **全部**环境变量，其中含 LLM/SERPAPI 密钥（G2 才把它收成白名单）。
   也就是说：一旦出现进程外执行，"带什么出去"立刻成为新的信任边界——
   这恰好是 ⑮ 必须先解决的问题，不是可以后补的细节。
4. `claw-code` 的对照（source-code-study §2.4）显示成熟实现把沙箱做成**能力探测**
   （探测内核能力，而不是看某个 binary 存不存在）；本项目连"执行位置"这个概念都没有，
   所以谈不上探测。

问题的形状因此不是「要不要上 gVisor」，而是**先有没有一个可以声明的位置**。
今天若直接给某条工具加子进程执行，改动会散落在 executor 的重试循环里，
下一条工具再要另一种 isolation 时又改一遍——端口缺失的代价就是这么还的。

## Decision（决策）

1. **端口在域层**：`agentix/domain/tool/sandbox.py` 定义 `ExecutionSandbox`（`kind` +
   `async run(handler, arguments)`）、可声明的档位词汇表 `SANDBOX_LADDER`
   = `in_process | thread | subprocess | container`、以及 `SandboxUnavailable`。
   域层零第三方依赖、不 import 其它层（ADR-0001 的依赖方向）。
2. **实现在基础设施层**：`agentix/tools/sandbox.py` 提供 `InProcessSandbox`、
   `ThreadSandbox` 与 `resolve_sandbox(kind)`。**G1 那条下放口径全项目只有一份**
   （`invoke_in_process`），`ToolExecutor._invoke` 也调它——不存在"第二套语义"。
3. **声明进 Spec**：`ToolSpec.sandbox` 默认 `in_process`；构造期只校验"是不是阶梯里的词"
   （拼写错立刻报错），**不**校验"当前能不能跑"。
4. **执行点 fail-closed**：`EXECUTION_SANDBOX_ENABLED`（默认关）打开后，executor 按声明
   解析执行位置；解析不到实现就抛 `SandboxUnavailable` 并**拒绝执行**，
   **绝不静默退回进程内**。拒绝排在观测钩子之前——它是一次闸门拒绝，不是一次执行。
5. **超时不归沙箱**：截断仍由 executor 外层的 `pooled_wait_for` 统一负责。
   若每个沙箱自备超时，「这条工具的 `timeout_ms` 到底生不生效」就又变成要读实现才知道的事。
6. **flag 关时逐位等价**：关 = 完全不查 `spec.sandbox`，走的还是原来那行 `_invoke`。

## Rationale（理由与被拒方案）

| 档位 | 买到什么 | 代价 / 前置 | 结论 |
|---|---|---|---|
| `in_process` | 零开销，现状语义 | 什么都不隔离：同进程、同 GIL、同 `os.environ`、同文件权限 | **默认档**（改它 = 改全项目每条工具调用的语义） |
| `thread` | 「别占住事件循环」——超时能截断，且**按工具声明**而非全局 flag | 仍不是隔离；线程池有自己的上限与排队语义 | **已实现**。它把 G1 从"实例级一刀切"降级成"工具级表态" |
| `subprocess` | 独立地址空间、`rlimit`（CPU 秒/地址空间/文件大小~~/进程数~~）、独立 uid、精简环境 | ① 每次调用一个进程 → 冷启动与序列化开销；② **环境白名单是前置**（G2 的教训），带什么出去必须显式；③ `rlimit`/`setuid` 是 POSIX，开发机是 Windows ⇒ 只能"能力探测 + 明确降级"，不能假装跨平台；④ 返回值必须可序列化，进程死了怎么取消 | **已实现（T2 ⑮，2026-10-25，`TOOL_SANDBOX_SUBPROCESS_ENABLED` 默认关）**。落地口径与原规划的四处差值见下「⑮ 落地」：进程数闸（`RLIMIT_NPROC`）**于 2026-10-26 补上，但带前置**（只在配了独立且非 0 的 uid 时落，计费单位是任务）、uid 降权是**可选旋钮**（默认 `-1` 不降权）、只读根/指定可写目录**没做**、被隔离代码**必须模块级可重建**（闭包/lambda/绑定方法/`__main__`/非函数可调用对象一律在执行点前拒） |
| `namespace` / `seccomp` 直接接线 | 内核级隔离，最接近"墙" | 需要容器特权或额外 capability，与同一份 compose 里"不额外给能力"的降权方向**正面冲突**（source-code-study X.1 的同一结论） | **拒绝**：在单机 compose 形态下，它买到的隔离要用更大的攻击面去换 |
| `container`（每调用一次） | 文件系统/网络/进程三重边界 | 冷启动以百毫秒～秒计；镜像供应链成为新依赖；挂载与凭据下发要单独设计 | **未实现（T2 ⑮ 之后的形态选择）**。当前所有工具的延迟预算（`timeout_ms` 默认 30s，检索类常为百毫秒级）容不下 |
| gVisor / Firecracker（microVM） | 不可信代码执行级隔离 | 需要专门节点与编排；运维面完全超出本项目 | **留给 T3**，且先决条件是"确实存在不可信代码工具"（今天是 `L3` 禁止注册，没有这类工具） |

被拒的还有一个更省事的方案：**不给端口，直接在 executor 里加一个 `if subprocess: ...` 分支**。
它今天能跑，但「执行位置」就永远不是一个可声明、可校验、可测的概念——
⑮ 到来时改的是执行链本身而不是新增一个实现，而 ADR-0001 的依赖倒置在这里就白写了。

## Consequences（后果）

**正面**

- 「这条工具在哪跑」第一次变成声明式、可 grep（`sandbox=`）、可被测试钉住的事实。
- G1 的一刀切有了替代写法：某条会占循环的 handler 声明 `thread`，不必为它把全实例语义换掉。
- 阶梯词汇表与实现集合的**差集是可见的**（`implemented_kinds()` 对 `SANDBOX_LADDER`），
  这使"T2 还差什么"能被机械检查，而不是靠文档里一句「尚未完成」。
- ⑮ 的落地成本从"改执行链"降为"加一个实现类 + 进注册表"。

**负面**

- **它没有带来任何新的隔离。** 端口打开后生产环境仍然没有墙：两档能跑的实现共享
  进程的一切。把它读成"沙箱已就位"是错误的——§24.2 的结论要等到 ⑮ 才改变。
  **[2026-10-25 更新]** ⑮ 已实现，这句话的前半段不再成立：`subprocess` 档现在真的隔离，
  但结论要换成另一句更窄的话——**默认路径仍然没有墙**（默认档仍是 `in_process`，
  ⑮ 的开关默认关，且它只挡住地址空间/CPU 秒/文件大小/环境/可杀性这五个维度，
  文件权限与出网仍共享，见下面「⑮ 落地」）。
- 多了一层抽象与一个 flag；默认关时它只是声明，不改变行为，但读代码的人需要知道这件事。
- `EXECUTION_SANDBOX_ENABLED=true` + 某工具声明了未实现档位 ⇒ 该工具**全量失败**
  （这是设计意图，不是 bug，但它是破坏性的：所以 staging 先开、生产按需）。

**缓解**

- staging override 已置 `true`（`docker/compose.override.staging.yml`），预发持续走这条缝；
  默认档 `in_process` 与关着逐位等价，因此 staging 打开不改变结果，只改变代码路径。
  **[⑮ 之后这条有了新含义]** 预发的端口开着，而 ⑮ 的三个键**没有**钉进 override
  （继承基线 `docker-compose.yml` 的 `False`/`-1`/空）。于是在预发给某条工具加
  `sandbox='subprocess'` 声明 ⇒ 那条工具在预发**全量失败**（执行点拒绝、不降级）。
  这是 fail-closed 的正身，但顺序必须反过来：先在 staging override 钉开
  `TOOL_SANDBOX_SUBPROCESS_ENABLED` 并重跑 `python scripts/gen_staging_matrix.py --check`
  （配置矩阵是生成物，约定 7），再改工具声明。
- 生产基线 compose 转发 `${EXECUTION_SANDBOX_ENABLED:-False}`：flag-off 等价性一路到部署层。
- 不把它列进 `main.py::_INSECURE_GATE_FLAGS`：判据是"关着会让实例不该对外"。
  它关着时的行为与今天的基线**逐位相同**，列进来只会稀释那条告警（与
  `TOOL_HANDLER_CONTRACT_ENABLED` 同一口径）。
- 回归：`tests/test_p114_execution_sandbox.py`（真跑 handler，不是断字符串——
  含「未实现档位声明时 handler 一次都没被调用」「`thread` 档真的让事件循环空得出来」
  「flag-on 默认档与 flag-off 返回值逐位一致」「阶梯与实现集合的差集口径」）。

## ⑮ 落地（2026-10-25）：这面墙第一次有了厚度

`subprocess` 档实现为 `agentix/tools/sandbox.py::SubprocessSandbox`，子进程侧入口是
`agentix/tools/subprocess_worker.py`。做了什么、没做什么，都按"能被复现"的口径写：

- **一次调用一个进程**，通信协议是 stdin 一条 JSON 请求 + stdout 一行带哨兵
  （`@@AGENTIX_SANDBOX@@`）的 JSON 应答 —— 带哨兵而不是"读第一行"，因为被隔离的业务代码
  会往 stdout 打日志（实测：`noisy` handler 打两行日志后返回值仍逐位正确）。
- **先落资源闸，再 import 业务代码**：`RLIMIT_AS=512MiB`、`RLIMIT_CPU=30s`、`RLIMIT_FSIZE=32MiB`
  在子进程里 `setrlimit` 后**回读**作为证据。Linux 容器实测回读 `[536870912, -1] / [30, -1] / [33554432, -1]`；
  墙内申请 4GiB 被 `MemoryError` 拦下（`blocked_by_rlimit=true`），不是"把机器吃满后一起死"。
- **进程数闸（`RLIMIT_NPROC`，上限 32 个任务）于 2026-10-26 补进同一批 `apply_gates`**，排在
  uid 降权**之后**——这个顺序是判据的一部分而不是风格：它按 real uid 计费，降权前落下去算的是
  父 uid 的账。三条前置（独立 uid / 非 0 / 计费单位是任务）见下「本 ADR 仍不声称已完成的部分」。
- **启动形态是脚本路径而不是 `python -m agentix.tools.subprocess_worker`**，这是本次唯一一处
  "实现比原规划更严"的修改：`-m` 会先执行 `agentix/__init__` 与 `agentix/tools/__init__`
  （整套业务工具、DB 驱动、loguru），于是资源闸落下去**之前**业务依赖已经进场，
  "闸先于被隔离代码"这条承诺当场失效，且每次调用多付一遍平台装配。
  实测同一台容器：`-m` 形态单次调用 p50 **517ms**、`import agentix.tools` 单项 **747ms**；
  脚本路径形态 p50 **≈50ms**（仓库在容器本机 FS；两轮分别 43.7 / 49.9ms）/
  **142–308ms**（Windows bind-mount，min 133–141ms，p50 随宿主 FS 抖动），
  子进程 `sys.modules` 里 `agentix.*` 与 `sqlalchemy/redis/neo4j/loguru/pydantic/httpx/langchain` **全空**。
  同一条 handler 走 `in_process` 档 p50 **0.001ms**、走 `thread` 档 **0.074ms** ⇒ 这一档的量级是
  "每次调用一个进程生命周期"，不是免费插座。数字与复现口径见
  `docs/runbooks/子进程沙箱取证.md`「数字」表。
- **环境变量与 G2（MCP stdio）共用同一份白名单**（`agentix/domain/tool/exec_env.py::OS_ENV_ALLOWLIST`），
  两个受众各留自己的 `extra_keys`、互不放宽。实测：父进程里 `DATABASE_URL`/`LLM_API_KEY` 有值时，
  墙内 `env_face` 回读的 `visible_keys` 只有 `HOME/LANG/PATH/PYTHONIOENCODING/PYTHONPATH`。
- **可杀**：`start_new_session=True` + `os.killpg(SIGKILL)`，父任务被取消时先杀进程组再 reap。
  实测（Linux）：取消一个 `sleep 30` 的墙内任务后，遍历 `/proc/*/cmdline` 找不到残留 worker。
- **能力探测即 ⑯**：`probe_subprocess_caps()` 判的是「这一档承诺的隔离维度能不能真落下去」
  （`resource` 模块 + 进程组 kill），不是「某个二进制在不在」。Windows 上两项都缺 ⇒
  执行点 `SandboxUnavailable` **响亮拒绝**：一次 handler 都不调、一个子进程都不起、
  `retryable=False`、报错点名缺失项与开关名。绝不"那就进程内跑吧"。
- **被隔离代码必须按 `module` + `qualname` 重建**，父/子两侧同源判据。六类形态在执行点前就拒：
  闭包/嵌套函数（qualname 含 `<`）、lambda、绑定方法（丢 `self` 等于换实现）、`__main__` 里的对象、
  运行时构造的可调用对象（`partial`、实例：拿不到 qualname）、**名字齐全但形状不对的类**
  （重建出来的是类本身，`Cls(args)` 是在新建对象而不是在跑那个工具）。
- **失败都带 `stage`**：`protocol` / `limits` / `reconstruct` / `invoke` / `serialize` / `crash`
  六类各有文案，父进程据此落 `ToolResult(success=False)`，不会只剩一个 exit code。
- **两侧各有体积闸**：请求 `1MiB`（`MAX_REQUEST_BYTES`）、应答 `8MiB`（父子同一常量），
  超限是明确错因而不是把父进程内存吃满。

### 本 ADR 仍不声称已完成的部分

- ⑮ **没有买到的**（约定 6 ①：白名单只覆盖它声明过的那个维度。这面墙挡住的是地址空间、CPU 秒、
  文件大小、环境密钥、可杀性，**以及有条件地挡住进程数**；**没挡住**文件权限与出网）：
  只读根文件系统、指定可写目录、网络默认拒绝——三件一起属 ⑰/T3。
  所以口径是"**是墙，不是笼子**"：handler 崩了、把内存吃了、把密钥读了，都出不了进程；
  但它想 `open()` 一个 world-readable 的文件或往外连，这一档不管。
- **进程数闸（`RLIMIT_NPROC`，2026-10-26 补上）是这一档唯一带前置的闸**，三条前置都是量出来的而不是
  推出来的：① **必须独立 uid**——内核按整个 real uid 在全机范围计费，共用父 uid（默认 `-1`）时
  上限设小会把"工具偶尔起一个子进程"变成偶发 `EAGAIN`（换台机器又好了，最难归因的一类），设大则
  根本不是约束；② **必须非 0**——uid 0 持 `CAP_SYS_RESOURCE`，内核跳过进程数检查，实测 root 把 soft
  写成 5 并回读到 5、随后照样连起 12 个进程一次不阻塞 ⇒ "调过 setrlimit" 不等于"闸生效"；
  ③ **计费单位是任务**（线程也算）——同一 uid 起 5 个线程回读进程 1 / 任务 6，soft=8 时先起 7 个线程
  再 fork 就第 0 次 `EAGAIN`，所以只看进程数会报"余量充足"而业务全崩。落不下的形态是
  `caps.nproc_gate.applies=false` + **告警一次**，判定与落闸面同源（约定 6 ④）；
  容器里可见的两个计数都只是**下限**（`no_headroom=false` 不保证 fork 得起来）。
  判据单源 `subprocess_worker.py::nproc_gate_plan`，取证见
  `docs/runbooks/子进程沙箱取证.md`。
- **uid 降权是可选旋钮**（`TOOL_SANDBOX_SUBPROCESS_UID`，默认 `-1` = 不降权，如实回读父进程 uid）。
  root 容器实测 `uid/euid` 都变成 `65534`；非 root 实测终局失败
  `[limits] uid drop to 65534 failed: ... (uid 降权需要 root；非 root 容器里请设 TOOL_SANDBOX_SUBPROCESS_UID=-1)`，
  不静默按父权限跑完。**注意**父进程侧判据是 `hasattr(os, "setuid")`（POSIX 恒真），
  所以非 root 时拒绝点在子进程侧，晚一步但仍然终局。
- 默认档仍是 `in_process`；**没有任何既有工具被改成走墙里**（开 flag 只是让"能走"，
  逐条 `ToolSpec.sandbox="subprocess"` 声明才真的走）。原规划里"MCP server 与一切外部工具默认
  `subprocess`"这一条**刻意没做**：那是行为变更，会改掉所有工具调用的延迟量级。
- 同名重复注册丢弃后一份 spec（含 `sandbox` 字段）——见 PROJECT_SPEC §24.2 **G14**，
  它让"声明了墙"这件事在极端注册顺序下不成立，是 ⑮ 之后最需要收口的一条。
  **2026-10-26 已收口为「可观测 + 可选设卡」**：两个注册入口默认打印
