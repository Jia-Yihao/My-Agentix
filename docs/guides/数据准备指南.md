# 数据集与数据准备（测试数据集领域）

> 本文承接 README 的数据准备章节。首页见 [README](../../README.md)。

本项目的测试数据集知识来自三类数据文件，分别对应图谱检索（graphrag）、社区摘要（LightRAG）与向量检索（kb）三条路径。数据已于 2026-07-27 由免费结构化开源数据集 **laubeing-droid/legal-cn-core-codices**（GitHub）自动填充：含《示例数据集 A》《示例数据集 B》《用工文档法》《宪法》四部测试数据全文与 67 个示例说明节点（含全文），数据条目正文均为真实文本，无 `【占位】` 残留。可复用 `scripts/data/build_legal_dataset.py` 从源重新生成。

## 已建模覆盖范围（2026-07-27 实际填充）

- **数据集**：《示例数据集 A》（1260 条 / 109 章节）、《示例数据集 B》（452 条 / 42 章节）、《用工文档法》（98 条 / 1 章节）、《宪法》（143 条 / 11 章节）——共 1953 数据条目（用工文档法仅 1 章节系源数据集未嵌章节标记所致，非缺陷）
- **数据分类**：示例文档异常、用工文档解除、盗窃、正当防卫、离婚财产分割（类别二 / 类别一分类）
- **示例说明**：《关于适用〈中华人民共和国示例数据集 A〉示例文档编通则若干问题的解释》（最高处理机构，法释〔2023〕13号）
- **机构**：全国人民代表大会、全国人民代表大会常务委员会、最高处理机构、最高监督机构、国务院、市场监管总局
- **关系**：`属于`（数据条目 → 章节 → 数据集）、`引用`（数据条目互引）、`对应数据分类`、`有示例说明`、`数据来源`、`上级数据集`

## 填充真实数据

1. **数据集 / 数据条目 / 章节 / 机构**：从 **国家测试数据集数据库**（`flk.npc.gov.cn`，全国人大官方、免费）获取数据集名、条号、条文原文、数据编号、生效日期、数据来源。
2. **示例说明**：从 **最高处理机构官网**（`court.gov.cn`）获取 name / 发布来源 / 日期 / 编号。
3. **数据分类分类**：参照《类别二案件数据分类规定（2020）》。
4. 将官方文本替换 `legal_seed.json` / `legal_lightrag_corpus.json` / `legal_corpus.txt` 中所有 `【占位】` 字段；`legal_lightrag_corpus.json` 使用 `title`（条目标题）/ `content`（条文全文）字段名。
5. 重新灌库：
   - **图谱**：`python scripts/legal_kg_to_csv.py` 生成 CSV → Dockerfile `neo4j_seeded` 阶段导入；
   - **向量库**：`kb_ingest` 重新导入 `legal_corpus.txt`（项目已生成 `.kb_milvus_ingested` 标记，表示 kb 向量库已初始化）；
   - **LightRAG**：Dockerfile LightRAG build 阶段读取 `legal_lightrag_corpus.json`。

> 提示：数据条目互引（`引用`）关系通常由 LLM 从条文正文中半自动抽取（识别"参见第X条"等表述），建议填完真实条文后统一补充。

## 本机（宿主机）跑通三条检索路径：灌库三步与核对口径

> 为什么单列这一节：容器视角下图谱与 Text2SQL 目标库由 Dockerfile/`init_mysql.sql`
> 建好，宿主机上没有那一步。2026-10-25 录制 `evals` 基线时踩到的就是这个缺口——
> 症状是「`graphrag` / `text2sql` 题一律给出看起来合理的兜底答案」，
> 而真因是库里根本没数据（目标库只有 10 条抽样条文、图是空的）。
> **跑录制的机器必须先做完这三步，再谈指标。**

| 路径 | 灌库动作 | 核对口径（本机实测） |
|------|---------|-------------------|
| 向量检索（kb） | `python scripts/demo/local_kb_demo.py seed --corpus data/kb/legal_corpus.txt`（SQLite + FAISS，指到 `data/demo/agentix_demo.db`） | `document` 4,865 / `chunk` 4,865（口径同 README §15.1；解析条目数不等会当场警告） |
| 图谱（graphrag） | `python scripts/legal_kg_to_csv.py` 生成 CSV → `neo4j-admin database import full`（容器内执行；含中文标签时 JVM 需 `LANG/LC_ALL=C.UTF-8`，Git Bash 调 `docker.exe` 需 `MSYS_NO_PATHCONV=1`） | 节点 2,201 / 关系 2,475，其中 `引用` **286** 条 |
| Text2SQL（SQL） | `python scripts/data/backfill_legal_sql.py --apply`（默认 dry-run；**只补不覆盖**，重复执行为 no-op） | `articles` 1,953 = 四部法 1,260 / 452 / 143 / 98，且 `laws`/`authorities` 元数据不被回填改写 |

两条不是「顺手修」的坑，记在这里免得重踩：

1. **`引用` 边会静默少 34 条**。`scripts/legal_kg_to_csv.py` 早期在单遍遍历里就地
   解析引用（「第 X 条」→ 节点 id），而被引条号有 34 个引用对指向**尚未登记**的
   条目（同数据集内、出现在更后的章节）。单遍顺解的结果是图谱只有 252 条 `引用`，
   SQL 侧 286 行却齐全——两个库都「有数据」，只有对比时才发现图谱缺边。
   现改为两遍：先挂起声明，节点全部登记后再统一解析（守卫
   `tests/test_p122_kg_csv_referential_integrity.py`，含专门复现前向引用的用例）。
2. **回填脚本的自然键映射写反过一次**（`{id: name}` 当成 `{name: id}` 用），
   「已存在」永远判不出来 ⇒ `INSERT` 撞 `UNIQUE` 把整批事务打回。这类
   「只补不覆盖」的脚本必须真的跑两遍并断言第二遍是 no-op
   （守卫 `tests/test_p123_legal_sql_backfill.py`，含 MySQL 真库的 `@integration` 用例）。

### 录制前还差一句：语料换域声明

出厂的 scope 文案（`agentix/application/agents/constants.py::SCOPE_DESCRIPTION`）是
**测试数据集**口径，而这里灌进去的是真法条。KB 子图的 guardrails 按旧域把
「一方以欺诈手段订立的合同能否撤销」判成越界，直接拒答且 0 引用（实测 L009/L012）——
那不是质量问题，是**语料边界没声明**。声明方式是
`KB_SCOPE_DESCRIPTION`（`general_handler.create_kb_query` 透传为 `scope_description`）；
`evals` 录制档已内置这句声明，手工跑别的入口时别漏。

### 空维度不是缺陷，是种子数据的缺口

`对应数据分类` / `有示例说明` / `上级数据集` 三类边与「关键词」字段在本机数据里为
0 行 / 空值——种子数据本身没填这些字段（见上文「已建模覆盖范围」）。
`graphrag` 题里问到这些维度时，**正确的系统行为是答不出并保留 0 引用**，
基线数字里的相应缺口来自这里，不在检索或门禁逻辑。
