# 面试 10 问（Agent Platform / My Agentix）

面向架构与 Agent 平台岗位的技术问答提纲；答案锚点均指向**本仓库真实模块**，
路径经 `tests/test_p41_doc_consistency.py` 守卫。

---

### 1. 为什么说 Agent Core 是 Harness 而不是「又一个 Agent 框架」？

Harness 五职责（Context / 规划 / 工具 / 验证 / 纠偏）映射到七个
`typing.Protocol` 端口（`agentix/domain/agent/ports.py`），实现可替换；
LangGraph 只允许出现在 `agentix/agent/graph/`，框架可换。

### 2. Context 如何防预算爆炸与提示注入？

`Context = Static Prefix + Trajectory`，超预算从轨迹尾部确定性截断，
大块证据进 `isolated_refs` 隔离区；状态栏键白名单（不信任模型自写）。
实现：`agentix/agent/context/engine.py`。

### 3. 五类记忆与读取时冲突裁决是什么？

Working / Episodic / Semantic / Procedural / User × user/task scope；
冲突在 **recall 时** 裁决而非写入时合并；remember 强制 PII 脱敏。
实现：`agentix/agent/memory/service.py`。

### 4. 工具智能（ACI）比 function calling 多做了什么？

负面描述（何时不能用）、参数保真（禁静默改参）、能力检索三层、
MCP 描述当不可信输入（防投毒）。实现：`agentix/tools/`（M1 自 infrastructure/tools 迁入；M6 后旧路径已删）。

### 5. 分层 Verifier 如何避免「模型自证」？

L1 结构 → L2 规则（`domain/policies/completion.py`）→ L3 grounding 纯函数；
Reviewer 只见结构化参数与证据，不见 Proposer 自述。
实现：`agentix/policies/verifier/layered.py`。

### 6. 四层故障与 Replanner 怎么协作？

API / 工具 / 上下文 / 控制流四层分类统一在
`agentix/orchestration/executor.py::classify_exception`
（曾误记为 capabilities 侧——那边没有此符号，见 executor 对照表 in `模块清单.md` §2）；
错误处理不再无限调 LLM，失败进 Replanner 产出**新** Plan。

### 7. HITL Sidecar 为什么强调上下文隔离？

Reviewer 独立 session，送审面只有 `to_public_dict()` 字段；
Approve/Reject/Edit/Resume 四裁决 + 进程重启恢复。
实现：`agentix/policies/hitl/sidecar.py`。

### 8. Long-running 事件模型的关键设计？

双时刻（occurred_at / received_at）、事件 key 去重、TTL 过期、
指数退避重试、虚拟身份 scope（看不到平台主凭证）。
实现：`agentix/agent/events/adapter.py`。

### 9. Pass@k 与 Pass^k 差在哪？1–2pp 提升算不算数？

Pass@k = 至少一次成功（能力上界）；Pass^k = k 次全对（稳定性）。
统计显著用两比例 z 检验，且绝对提升需 ≥2pp 才 practically meaningful。
实现：`agentix/domain/evals.py`、`evals/run_eval.py`。

### 10. Continuous Evolution 如何保证「进化不拆房」？

在线循环 **零写能力**；离线 聚合→提案→回归→灰度；
三道防线：证据≠指令、staging 隔离、验证器逻辑路径黑名单。
实现：`agentix/agent/evolution/loop.py`。

## 附：讲一个"坑"，而不是讲全貌

> 面试里"介绍这个项目"的最优解不是把 §1 那张表背一遍，而是**用一个具体坑证明
> 治理点不是装饰**。下面三段是可直接口的三句话版本，每句都钉在真实代码行与真实
> 测试函数上；**"没断什么"必须一并说出口**——把没覆盖的当成覆盖了，是这类叙事唯一
> 会被当场戳穿的地方。

### 11. 坑一：取消不是"标记一个 flag"（推荐主叙事）

1. 最初我以为取消就是把运行状态写成 `CANCELLED`，做完才发现状态是终态了、底层那个
   asyncio Task 还在睡它的 30 秒——对外已经报"已取消"，工具调用和 token 还在继续花。
2. 现在 `ControlPlane` 通过 `bind(run_id, task)` 持有 Task 句柄，`cancel()` 里
   `task.cancel()` 之后**再 `await task` 收口**，让"报取消"和"真的停了"是同一件事
   （`agentix/runtime/control_plane.py:234-249`，注释原话是"避免『已报取消但仍在跑』的假象"）。
3. 守卫测试断的是**可观测的事实**，不是时序承诺：`tests/test_p31_control_plane.py:332`
   `test_cancel_actually_interrupts_bound_task` 让 worker 自己在
   `except asyncio.CancelledError` 里置一个 `Event`，`cancel()` 返回后断言事件已置位、
   `task.cancelled() or task.done()`，旁边另有三条同伴用例（`:318` 终态、`:326` 幂等、
   `:353` Task 抛异常时取消不挂）。

**必须一并说出的非声称**：这条测试**没有**断"100ms 内停下"，也**没有**断"取消后预算不再增长"。
预算台账确实在 `agentix/domain/runtime/budget.py:22` 的 `BudgetManager`
（`used_steps` / `used_llm_calls` / `used_tool_calls` / `used_tokens` / `used_cost_usd`
五个计数 + `_t0` 时限），但"取消 ⇒ 计数冻结"这条链路今天没有测试覆盖——想补的话是
`test_p31` 里加一条断言，属于测试基线变更，按 AGENTS.md 纪律 5 要先经维护者同意。
顺带一个真实口径修正：README §1 概览表里旧写作"四维预算"，现已统一为"六维预算"——`Budget` 值对象有
**六个** `max_*` 维度（`steps` / `llm_calls` / `tool_calls` / `tokens` / `latency_ms` /
`cost_usd`，见 `agentix/domain/runtime/budget.py:35-43`；0 表示该维度不限额）。

### 12. 坑二：新 flag 关掉后必须和基线逐位一样（备选叙事）

仓里所有行为变更走"新 flag + 默认关 + 显式启用"，这条纪律不是口头承诺：
**36 个测试文件里出现 75 次"逐位等价"**（另 14 个文件用 `byte_identical` / "逐字节"字样；
两条计数命令见第 15 条的表，数字会随批次漂，报之前重跑命令）。
两种典型断言形态——

- 字符串面：`tests/test_p113_where_parametrization.py` 的第 2 层要求 flag-off 时
  产出的 SQL 与加固前**逐字节相同**且 `_bindparams` 为空，新字段 `filters` 在关着的
  flag 下被**显式拒绝**而不是静默忽略（静默忽略=功能没生效却报告成功）。
- 调用次数面：路由 fast-path 的 flag-off 用例是
  `tests/test_p94_llm_optimization.py::test_flag_off_greeting_still_builds_llm`——
  寒暄句在关着时**照样要构造 LLM**；开关消融那一侧更进一步，用 `_boom` 哨兵把
  `get_llm_client` 换成"一调用就抛"（`tests/test_ablation_wiring.py:153`），
  钉死"命中 fast-path ⇒ 零模型构造、零分类请求"。

讲法：只测"flag-on 行为对不对"的灰度是假灰度，因为线上 99% 的时间跑的是 flag-off 路径；
**基线等价要有测试钉住，否则"默认关"这三个字没有任何可验证含义**。

### 13. 坑三：路由静默兜底——同一份代码，换套 SDK 就不走模型了（备选叙事）

三句话版：**L1 路由调 `with_structured_output(Router)` 时不传 `method`，于是"本地跑不跑得通"
由已装的 langchain-openai / openai 版本组合决定，而失败被 `agentix/application/agents/router.py`
的 `except`（240–243 行）吞成 `fallback_router`，日志只有一行 WARNING，指标面上与"模型真判了
kb-query"同形，业务表现是"所有问题都进知识库"；我先在 Anaconda 栈（openai 1.47.0 /
langchain-openai 1.1.6）上踩到——默认 `json_schema`
分支要调 `chat.completions.with_raw_response.parse()`，那个 SDK 里没有这个方法，每次分类都
`AttributeError`，改钉 `function_calling + tool_choice="auto"` 才通（LM Studio 只收字符串
tool_choice，对象形式实测 400）；换到仓库登记的 `.venv`（openai 1.109.1 / langchain-openai 0.2.14）
同一份补丁又坏了——这个版本连构造都不接受 `tool_choice` kwarg，但它的 `json_schema` 是通的。


收口方式不是写死版本号，而是**按能力探测**：`scripts/demo/local_kb_demo.py` 的
`_pick_local_structured_output()` 先探 SDK 有没有 `with_raw_response.parse`、再探那套库能不能
用给定 kwarg **构造出**结构化输出链（只构造不 invoke，不发请求），选中的组合连同环境指纹一起
打印。**故障可定位的判据也顺手做了**：`ask` 输出的「判定依据」行写的是模型自己给的理由文本，
如果它变成光秃秃的 `kb-query`，就说明又退化成兜底了。

可核对的数字与**非声明**：23 题在两套栈上**逐题位次与检索集合 0 处差异**（质量对栈不敏感），
但检索 P50 是 100.3ms vs 2310.8ms（延迟对栈极敏感，归因见 README §15.2 口径③——每次搜索都重建
embedding 客户端，代价被 SDK 放大）。**"静默"这一半已在 2026-10-25 收口**：兜底现在计
`router_fallback_total{reason}`（默认启用，无行为变更，守卫 `tests/test_p118_router_fallback_metric.py`）；
但仍有**一条已知空洞**——非法类型且不是 `Router` 实例时校验异常冒出节点、既不兜底也不计数
（`test_p118` 用 characterization 用例钉住现状）。**没有**测试钉住"LM Studio 的结构化输出形态"：这是演示层
适配，不是生产契约，生产走 DeepSeek/OpenAI 兼容 tool-calling，出厂形态本就通；也不声明
"探测永不出错"，它只保证选不出组合时**打印出来**而不是静默退化。

### 14. "为什么做这么大"——被问到时怎么收

一句回答：这个项目要验的不是"能不能拼出一个 Agent demo"，而是"一个 Agent 跑起来之后
谁替它兜底"，所以取消、预算、重试、降级、评测、可观测做进了运行时本身，而不是留在
应用层各写一遍。

两句代价：**仓库变大、演示变难**——所以 README 顶部现在先给一条 3 命令的最小切片
（SQLite + FAISS + 本机 LM Studio，不碰 Neo4j/Milvus/DeepSeek），GraphRAG、Text2SQL、
MCP、多智能体全部降级成"可选能力清单"；被问"是不是过度设计"时，答案落在证据形态上：
**过度设计的证据是"没有守卫的抽象"，而不是"抽象多"**——坑一/坑二各有真实测试行号可指，
flag 关掉能回到逐位等价的基线；坑三是**没有测试可钉**的那一类（演示层适配，不是生产契约），
所以它的证据形态只能是环境指纹 + 逐题对拍数字，讲的时候要把这个差别一并说出口。

### 15. 测试数量怎么用（`N passed` 是个口径数字，不是能力数字）

不要把套件总数当卖点报出来——它只说明"这一天这台机器上离线套件是绿的"。
**总数唯一真源是 README §11**（本文件按 `tests/test_p41_doc_consistency.py` 的
单源约定不复述数字，要用的时候去那里取）。可独立复核的结构量是另外三个，
每个都带现测命令：

| 项 | 数值 | 口径（命令即口径） |
|---|---|---|
| 测试文件 | 215 | `find tests -name "test_*.py" \| wc -l` |
| `def test_` 定义数 | 4,240 | `grep -rE "^[[:space:]]*(async )?def test_" --include="test_*.py" tests \| wc -l` |
| 用到 parametrize 的文件 | 52 | `grep -rl "@pytest.mark.parametrize" --include="test_*.py" tests \| wc -l` |
| 治理点分布（节选） | 取消 4 / 预算 7 / HITL 15 / flag 等价 36 文件 | 分别锚在 `test_p31_control_plane.py`（4 条 cancel 命名用例）、`test_r3_agent_runtime.py`（34 条中 7 条 budget 命名）、`test_agent_phase8_hitl.py`（15 条）、"逐位等价"字样扫描（75 处） |

**定义数 ≠ 采集用例数**：README §11 那个 `passed` 数比 4,240 高出来的部分，全部来自
`@pytest.mark.parametrize` 与类内异步方法的展开；报数时把两者混在一起，就等于把
"我们写了 4 千个断言"和"套件跑出 4 千多条用例"当成同一件事。

一句收口：**按治理点报，不按总量报**——"取消能真打断 Task"配一个测试函数名，
比一个巨大的总数可信得多。
