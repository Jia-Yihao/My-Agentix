## 2. 可扩展优化点（2026-10-04 新增清单）

> 每条含：**现状 → 方案与方法实现 → 可扩展方式 → 验收 → 风险与回退**。标「拟增」的键/文件是提案，落地时按四原则五处同步。

### P0（配置或小改即可，先做）

**E1 · 工具轮内并发灰度推广**（类型：纯配置）
- 现状：机制与授权门已齐（§1.2），默认 1 = 串行基线。
- 方案：对低风险工具集（只读检索/查询类）在联调与压测环境将 `AGENT_TOOL_ROUND_CONCURRENCY` 提到 2-4，观察 p95 与错误率后再动生产默认值。
- 可扩展方式：round_gate 的授权语义即扩展点——后续可按工具风险分级（高风险工具强制串行）细化。
- 验收：golden 离线评估零回归；同题串行/并发各跑一轮对比 p95。
- 风险与回退：并发共享副作用的工具（写库/发通知）须靠既有风险门拦住；回退 = 置回 1。

**E2 · schema 缓存 TTL 生产化**（类型：配置 + 小改）**——主动失效入口已落地（2026-10-26）；TTL 对齐 300s 仍未动默认值**
- 现状（落地前）：`TEXT2SQL_SCHEMA_CACHE_TTL_SECONDS` 默认 0（关），`NEO4J_SCHEMA_REFRESH_SECONDS` 默认 300s——两套 schema 缓存节奏不一致，且**都只能"等 TTL 到点"**：DDL 之后旧 schema 还能继续服务一个窗口期，当时唯一的立即生效手段是重启进程（连带清掉别的缓存）。
- 方法实现（真实锚点，原「拟增」字样按 §5 第 6 条清除）：
  - text2sql 侧 `…/components/text2sql/schema_retrieval/node.py::invalidate_schema_cache(database_url=None) -> int`——按 `f"{database_url}|"` 前缀选条目、返回**真清掉的条数**（清不到照实报 0）；`schema_cache_size()` 供报告核对剩余；包门面 `schema_retrieval/__init__.py` 导出这两个符号。
  - Neo4j 侧 `kg_neo4j_conn.py::invalidate_neo4j_schema() -> bool`——**打标记而不是重建**：`_schema_stale` 由 `_schema_refresh_due()` **优先于 TTL** 消费（默认 TTL 关着时入口照样有效，否则它在默认部署里是装饰品），标记在下一次取用时清掉（不做重试风暴）；无实例时返回 `False` 且**不连接**。
  - 统一入口 `agentix/application/services/schema_cache.py::invalidate_schema_caches(database_url=None)` → `{text2sql_schema_cleared, text2sql_schema_cache_remaining, neo4j_schema_marked_stale, errors}`；任一侧抛错只进 `errors`、**不外抛**（纪律 2），失败侧的字段**全部**置 `None`，不留半个像真数的值。
  - 运维面 `POST /api/v1/ops/schema-cache/invalidate`（`agentix/interfaces/http/ops_router.py`，继承 `/ops` 的 `Depends(verify_api_key)`）：报告自带 `ok` 位；两侧全炸也回 200 + `{ok: false, error}`。**刻意不与 `/ops/memory/clear-user` 的「删除失败 ⇒ 500」同款**——清除结果必须可信，而清缓存失败不改变正确性（迟早按 TTL 收敛）。
- 仍是灰度决策（本批**没有**动默认值）：把 text2sql TTL 从 0 提到 300 是**行为变更**（缓存自此开始生效，读旧 schema 的机会从 0 变成 ≤300s），按 §5 需要 E5 基准 + 联调环境 p95 取证才能谈生产默认。本批只把「改表 → 主动清 → 立即可见」这条路修通，让那个窗口期从"最多 300s 且无人可管"变成"最多 300s，且随时可手动归零"。
- 可扩展方式：入口与 HTTP 面解耦（脚本/导入任务可直接调 `invalidate_schema_caches`）；后续可挂 schema 变更事件，或在 `scripts/data/backfill_legal_sql.py` 灌库尾部自动调一次（**未做**，属部署选择）。
- 验收（已跑，2026-10-26）：`tests/test_p126_schema_cache_invalidation.py` **13 passed**；相关面 p85/p12/p64/p96/v1 鉴权/p68/p82 合跑 **195 passed**；`test_code_hygiene` 14 passed（本批新文件曾以 `%s` 写 loguru 日志被抓红，已改 `{}`）。**变异反证三组、红因各不相同**：① Neo4j 侧「stale 优先」退回只看 TTL ⇒ 2 红（`forces_the_next_get_to_refresh` / `works_even_when_periodic_refresh_is_off`）；② text2sql 失效桩成"报 0 但什么都不清" ⇒ 3 红（可见性 / 按库收窄 / 门面同一性——第 3 条是变异本身造出的 node↔包分家，正是那条钉子要抓的形态）；③ 失败分支去掉 `remaining = None` ⇒ 1 红（`reports_none_for_every_one_of_its_fields`）。
- 风险与回退：按库收窄是**刻意的**——无条件全清会让一次调用打掉所有目标库的热缓存，那是可被反复利用的延迟放大面；默认姿态零变化（无新配置键 ⇒ 不进纪律 4 的五处同步；默认不缓存；端点不调用即无影响）。回退 = 不调用端点（回到纯 TTL 语义），或撤掉本批四个文件（`schema_cache.py`、`node.py`、`kg_neo4j_conn.py`、`ops_router.py`）+ `tests/test_p126_*`。

**E3 · HTTP 出口连接复用（连接池化）**（类型：代码 + flag）✅ 已落地（Phase H W3；**本条目原写「拟增 `HTTP_CLIENT_POOL_ENABLED`」——那个键从来没有存在过**，实际落地的是 `SHARED_HTTP_MAX_CONNECTIONS`。留着旧名的代价不是难看：照它设环境变量会静默无效，而"我明明开了池化"是最难查的一类）

**E7 · 语义结果缓存**（类型：新能力 + flag）✅ 召回级已落地（2026-10-26，默认关）
- 现状（落地前）：有 embedding 精确缓存（§1.4），无「问题语义相近 → 复用近期答案」能力；重复问法仍全链路重跑。

- 落地形态（本批实际做的选择，与原方案的两处差异）：
  - **接入点是 `chat_service.retrieve_scoped_docs_cached`，不是 `retrieval_hybrid.py`**。理由是位置：
    精确 Redis 键之后、miss 主体之前——精确键命中连 embedding 都不必算，语义层只该接住
    "换了问法问同一件事"那部分流量；插在 hybrid 内部等于给每次命中白付一次 embedding。
  - **存储是进程内分桶，不是 Redis**。既有 `agentix/application/services/redis_cache.py::RedisSemanticCache`
    是**答案级且至今未接线**的孤岛（自带 async 客户端、自己 POST `OPENAI_API_BASE` 取向量、
    绕过 E4 的内容缓存与 LM Studio 口径），把它接起来要同时引入第二份 Redis 客户端与第三份余弦实现，
    违反纪律 6 ④；本批因此新建 `agentix/retrieval/infra/rag/semantic_cache.py`（判定面 `best_match`
    纯函数 + 存储面 `SemanticRecallCache`），"命中判定与存储解耦"照原方案保留——换 Redis 共享只替存储面。
- 三条不可让的口径（各有守卫）：**τ 只有一个源**（比较只发生在 `best_match` 里，调用方不许二次判分）；
  **权限隔离是结构性的**（bucket 由与精确键**同一个** `_retrieval_cache_key(question_norm=None)` 派生，
  摘要位写成字面量 `sem` ⇒ 与真实 24 位十六进制摘要不可能相撞；自己拼一份"租户+kb+权限"串就是
  给隔离造第二源，而第二源出错的方式是**跨权限命中**、不是报错）；**向量空间必须同源**
  （bucket 末尾带 `|m:<model>`，换模型即换桶，不共池）。
- 键：三键同 E4 只住 `agentix/retrieval/settings.py`，**不放**统一配置层；τ/TTL 的非法值校验
  刻意**不以 flag 为前提**（与 E4 的 `_MAX` 同口径：τ<=0 是"任何问法都算命中"，τ>1 是"开了等于没开"，
  TTL<=0 让写侧被拒、读侧恒判过期——三者都是配错，不是"关"的表达方式）。
- 计数面：复用既有 `cache_hits_total{cache_type}` / `cache_misses_total`，取值新增
  **`semantic_recall`**（刻意与既有 `"semantic"` 分开——那个值属于未接线的答案级类；打进同一条
  时间序列就说不清命中率是谁的）。**零新 label**，纪律 3 白名单未动。
- 验收（`tests/test_p128_semantic_recall_cache.py`）：相似问法命中 + **不相似必须不命中**的反例 +
  τ 边界（== τ 算命中）+ 维度不符/负相似永不命中 + 空结果不回写（否则"检索为空"会粘在 TTL 里，
  灌库完成也读不到新东西）+ 坏载荷按 miss 回退真检索 + flag 关时连 embeddings 实例都不构造
  （**数构造次数**而不是"一调用就 raise"——raise 会被 fail-open 咽成 `None`，两种结局长得一样；
  链路侧才用 raise 桩，那一段没有 fail-open 包装）+ 桶间隔离与模型不共池 + TTL 读取时算 + 有界逐出。
- 风险与回退：**未压测**，且 τ=0.95 是保守出厂值**不是调优值**——E5 的 `tests/test_perf_smoke.py` 量的是
  关键调用时延的数量级，语义缓存需要的是**命中率与串答率**，这两组数仓库里没有（README §11 的金标只测
  召回质量，不测"换了问法之后命中的是不是同一件事"）。多 worker 各持一份进程内缓存，
  不共享（换来的是零新依赖、零跨进程失效协议）。回退 = flag 置 false，路径与本批之前逐位等价。
- 残余项（不在本批顺手做，理由如上）：`RedisSemanticCache` 的答案级接入与 `_cosine_similarity`
  那份重复实现的合并；两者都等"有人接线"再动，否则改数值口径没有可验证的收益。

- **串行主干**：L1 → L2 → L3 → L4，再 L5 → L6，之后 L7 → L8 → L9。这条链断一环，后面的降幅都归不到因。

### 6.6 意图路由的分层取舍

现在全部流量压在最贵的一层：每次请求都先走一次 LLM 结构化分类，`_fastpath_router` 写好了却由 `ROUTING_FASTPATH_ENABLED` 关着，中间那层轻量语义路由根本不存在。分层漏斗要解决的不是「换个更准的分类器」，而是「让绝大多数请求在最便宜的一层被解决」；所以这一节只回答一件事——四层里哪层现在该补、哪层该等，以及等什么。

| 层 | 工业界职责 | 本项目现状 | 裁定 | 落点 |
|---|---|---|---|---|
| L0 结构化入参 | 前端或 API 直接给意图，不经识别 | 无此类入口 | 不做 | — |
| L1 确定性 | 寒暄、命令、目录 cue、格式强约束的请求 | `agentix/application/agents/router.py` 的 `_fastpath_router`：不超过 60 字、寒暄精确匹配、单条法条且无推理词；命中记 `llm_calls_saved_total` | 对齐词表后打开 | L11 前置 |
| L2 轻量语义 | 例句 embedding 或 TF-IDF + 逻辑回归 | 无 | 暂不补，等 L12 的按类读数 | 解锁后复用 L12 语料 |
| L3 大模型 | 单次结构化分类，处理歧义与多意图 | 单次结构化输出；`confidence` 字段存在但提示词禁止模型输出 | 保留，补置信与分箱 | L11 |

**L1 的问题在词表，不在逻辑。** 三个正则（寒暄精确匹配、数据条目引用、推理词排除）是法律业务域留下的，而路由现在描述的对象换了一批，两边不是同一批词。打开之前必须让两者对齐，否则命中的是错的那一类——那比不开更坏，因为错路由不会报错，只会沉默地走错链路。

**L1 已经自带读数，别浪费。** `record_llm_calls_saved` 记的是「省掉了多少次分类调用」，这正是漏斗唯一现成的观测点。L11 应当把它扩成按层计数的流量账本（L1 命中、L2 命中、L3 落地），否则「token 降了多少」永远归不到层，也就进不了简历里那句「路由调用占比」的表述。

**先不补 L2 的理由是读数，不是成本。** 现在的路由准确率在六成上下，远低于单次结构化分类应有的水位——这说明问题在提示词、白名单与兜底，不在「用错了方法」。在 L12 的按类报表出来之前加一层，等于在一个还不知道错在哪的系统上叠加第二个误差源。解锁条件写死：L12 出报表后，若某几类持续稳定可分，直接用同一套语料（每类不少于三十条）建例句库，零新增标注；若错的集中在边界样本（既像两类的问题），L2 帮不上，只有 L3 的候选集加验证有用。这条条件要写进 L12 的验收，否则以后一定有人跳过它直接上 embedding。

**置信度的两处默认值必须先统一。** `agentix/orchestration/langgraph/lg_states.py` 里 `confidence` 一处是可空且默认空、一处默认 0.0。分箱校准会同时拿到「缺失」和「零」两种假值，两种都不该进分档统计。先定一个可判定的空值语义（缺失就是缺失，不是零分），再谈阈值，否则校准曲线是假的。

**路由由代码执行，不由模型选分支。** `route_query` 是条件边，这一点已经对了；不要把白名单判断挪进提示词——挪进去的代价是同输入不同输出、无法单测、改规则必须改提示词。

**分类、槽位、路由是三件事。** 本项目 `Router` 只输出 type 与 logic，槽位不在分类器里，这点比多数实现干净，守住即可：槽位归上下文引擎与会话状态，缺了就走澄清，不让分类器顺手编参数。

**边执行边修正：不采纳。** 它把「分类错的代价」换成「走错一步再纠正」，前提是工具幂等或可回滚；本项目有建单、发消息这类副作用工具，纠错成本高于收益。记在这里，是让它下一次被提出来时有个明确的否决理由。

### 6.7 与既有台账的边界

§4.1 的台账管「性能开关的默认值该不该动」，本节管「指标能不能采、能不能归因」，两者的判据不同：前者要「效果取证」，后者要「读数可复现」。因此本节不重复登记 E 系列任何一项，也不因为 L9 提到缓存就顺带改 E7 的 τ。三处值得单独点名的「接线型缺口」——MCP 客户端齐全但零引用、`conversation_summary` 处理器注册却无投递点、observer 27 行且无调用方——都属于「代码写好了、没人调用」，修它们不需要新设计，只需要把调用点接上并补一条守卫；这也正是为什么第二段的预估比第一段短，却更依赖前置。

## 8. Agent 内核、工具管道与上下文（M4，2026-10-28 登记）
