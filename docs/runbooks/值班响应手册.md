# Oncall Runbook —— 告警响应与降级排查树

> 适用：docker/monitoring/alert_rules.yml 全部 10 条告警 ｜ 更新：2026-10-28（补 Celery 队列积压 / 不排空两条，含 exporter 前置三件）

## 响应总原则

1. 先看 `/readiness` 与 `/metrics`（免鉴权），再进容器日志；
2. 降级 ≠ 宕机：多数降级路径下**核心问答仍可用**（分级降级设计），优先恢复依赖而非重启应用；
3. 每次处置按 `docs/runbooks/故障复盘模板.md` 留档。

## 告警 → 动作映射

### My AgentixBackendDown（critical）
- 现象：Prometheus 抓取 `backend:8000/metrics` 失败 1 分钟
- 排查：`docker ps`（容器退出？）→ `docker compose logs backend --tail 100` → 启动期失败多半是 selfcheck/secret_key fail-fast
- 恢复：修复配置后 `docker compose up -d backend`；非配置问题抓 core dump 截图留档再重启

### My AgentixHighErrorRate（critical，5xx > 1% 持续 5min）
- 排查：`http_requests_total{status=~"5.."}` 按 endpoint 维度拆 → 定位异常路由 → 日志搜 trace_id（响应体会回显 trace_id）
- 常见根因：LLM 上游超限/断连、Redis 分片故障、DB 连接池耗尽

### My AgentixHighP95Latency（warning，P95 > 10s 持续 5min）
- 排查顺序：`llm_request_duration`（上游慢？）→ `rag_retrieval_duration`（索引劣化？）→ `llm_concurrency`（并发排队打满？说明 LLM_MAX_CONCURRENCY 偏小或上游变慢）
- 恢复：上游慢 → 观察熔断器是否打开（见下）；并发打满 → 临时调大 `LLM_MAX_CONCURRENCY` 或扩容上游配额

### My AgentixRateLimitStorm（warning，>5 次/秒）
- 排查：`rate_limit_triggered_total{scope}` —— `global`=全局限流中间件触发，`chat`=检索域聊天路由
- 定位滥用 IP：日志按 `X-Forwarded-For` 首跳聚合
- 恢复：单点滥用 → 边缘封禁；正常高峰 → 调 `RATE_LIMIT_GLOBAL_RPM/BURST`

### My AgentixComponentDegraded（warning，新降级事件）
- `component="checkpointer"` → 会话不持久化（MemorySaver 兜底）。排查树：
  1. `_degraded_reason`（日志搜 `checkpointer`）：
     - `langgraph-checkpoint-redis not installed` → 镜像依赖缺失，重建镜像
     - `CHECKPOINTER_TYPE=memory (explicit)` → 有人改了配置，确认是否有意
     - `RedisSearchError: ... Cannot create index on db != 0` → **`REDIS_CHECKPOINT_URL` 指到了非 0 库**。
       RediSearch 只能在 db0 建索引，改回 `/0` 并重启即可（R3.2 曾用 db2，2026-10-23 已修正）
     - `RedisSearchError: ... unknown command 'FT.INFO'` → 连上的是不带 RediSearch 的普通 Redis
       （例如误用 `redis:7-alpine`），换回 `redis/redis-stack-server`
     - 其他异常类名 → 看 `REDIS_CHECKPOINT_URL`（db0 分片）连通性
  3. 降级单例是**粘的**：同一进程内 Redis 之后恢复也不会重试，必须重启服务
  2. 核心问答不受影响，但**重启即丢进行中会话**——尽快恢复
- `component="chat"` → 检索通道部分失败（general_handler 标记）。查 `rag_retrieval_*` 分项

### My AgentixCircuitOpen（critical，熔断器 OPEN）
- 现象：`circuit_state{name}=2`，下游连续失败达阈值，请求快速拒绝走降级响应
- 排查：熔断器 name 指向的下游（LLM/embedding）→ 直接探活上游 API
- 恢复：上游恢复后半开探测成功自动 CLOSED；**不要手动 reset 生产熔断器**（掩盖真实故障）

### My AgentixGroundingLowScoreSpike（warning，30min 内 grounding 低分答案 > 10 次）
- 现象：`grounding_low_score_total` 突增——拒答锚点头部依据不足的信号
- 排查：核对 kb 文档/权限域变化、grounding 阈值配置漂移、上游模型漂移；查观测面板 grounding 低分 trace
- 恢复：锚定阈值配置回滚 → 补语料/修权限 → 观察 30min 曲线回落

### My AgentixGatewayFallbackCascade（warning，15min 内 fallback > 5 次）
- 现象：主模型连续失败、二道兜底接管——成功率假象，主模型可能不可用
- 排查：日志与 metrics 中 `primary_model` / `fallback_model` 分层对比 → 主模型 API key/配额/网络
- 恢复：主模型恢复即自动归位；持续则按预案切换主模型配置（`docker compose up -d backend`）

### My AgentixCeleryQueueBacklog（warning，队列长度 > 20 持续 10min）
- **先确认这条规则是不是「无数据」**：指标 `celery_queue_length` 由 broker 侧的 **celery-exporter**
  导出，**本仓** `agentix/observability/metrics.py` 不暴露它，`docker/monitoring/prometheus.yml`
  里也没有该抓取目标 ⇒ **未部署 exporter 时这条规则恒为「无数据」，不触发也不报错**。
  「没告警」不等于「没积压」：先看面板上这条序列有没有数据（无数据即从未被评估）。
- 使它可评估的三件前置（与 `docker/monitoring/alert_rules.yml` 末尾「队列规则前置说明」逐条一致，缺一即仍不触发）：
  1. 部署 celery-exporter，`BROKER_URL` 指向 retrieval-worker 用的同一个 broker（`CELERY_BROKER_URL` 默认 `redis://redis:6379/1`）；
  2. `docker/monitoring/prometheus.yml` 增加抓取 job（`celery-exporter:9808`）；
  3. worker 以 `-E/--events` 启动（compose 的 retrieval-worker command 目前**没有** `-E`），或改用直读 Redis 的 exporter。
- 处置方向（顺序别倒）：`docker ps` 看 retrieval-worker 容器状态/副本数 → `celery -A agentix.retrieval.infra.tasks.celery_app.celery_app inspect ping` → Redis（db1 broker）连通性 → 再看作业是否卡在 Milvus/MinIO 依赖上
- **扩副本前**确认 Redis broker 与索引写锁没有互相争抢：两个 worker 并发写同一版本目录会把积压换成另一个故障
- 阈值口径：20 = 默认容量（`RETRIEVAL_WORKER_REPLICAS=1` × `--concurrency=2`）的 10 个串行波次；改副本/并发后按同一式子重算，不要凭感觉调

### My AgentixCeleryQueueNotDraining（critical，队列长度 > 0 持续 30min）
- 数据前置同上（celery-exporter；未部署前置时恒为「无数据」，不触发也不报错）
- **因果口径**：连续 30 分钟非空只证明**持续积压**，不证明「消费端停摆」——两种成因形状相同：
  1. 消费停摆（worker 掉线/卡死、broker 不可达）：入队照旧，出队为零；
  2. 持续饱和（入队速率长期高于消费吞吐）：worker 一直在消费，只是单作业耗时长于到达间隔，队列稳定停在非零水位。
- 区分动作：① 停摆嫌疑 → 查 retrieval-worker 容器状态/存活、`celery inspect ping`、Redis db1 连通性，
  并看 `acks_late` 下 `visibility_timeout` 的重复投递（同一 job 被重投会占用消费位）；
  ② 饱和嫌疑 → 查 `RETRIEVAL_WORKER_REPLICAS` 与单作业耗时是否已接近 1800s 上限。
- 处置顺序：**先排除停摆再扩副本**——停摆时扩副本无效，只会把积压摊到更多卡住的 worker 上
- 阈值口径：`for: 30m` 对齐 `INDEX_JOB_TIMEOUT_SECONDS=1800s`（单个作业的硬上限）；阈值只看队列键长度，
  已被预取未 ack 的作业不在其中（见 `docker/monitoring/alert_rules.yml` 前置说明第 4 条）

## 升级路径

15 分钟未定位 → 冻结变更 + 导出 `docker compose logs` 全量 + `curl /metrics` 快照留档。
