# 密钥管理 Runbook（企业级评估 §4.3）

> 现状：密钥经 `.env` 明文 + compose `env_file` 注入。本文是过渡方案 + 轮换流程；
> Vault/AWS Secrets Manager 集成为正式方案（待立项，见文末）。

## 当前防线（已有）

1. **dev 缺失**：启动期临时生成强随机密钥 + 强告警（`resolved_secret_key`，P0-6）；
2. **生产缺失**：fail-fast 拒绝启动（staging 同口径，见下）；
3. **字段集合自检**（p35）：`.env` 静默回落默认值在启动日志显式告警；
4. **第三方可执行体不再继承密钥**（§24.2 G2）：`MCP_SUBPROCESS_ENV_SCRUB=true` 时
   MCP stdio 子进程只拿 `client.py::OS_ENV_ALLOWLIST` 里的键（起进程 / 找包 / 编码 /
   证书 / 代理），`LLM_API_KEY` / `SERPAPI_KEY` / `DATABASE_URL` 一律不进子进程。
   **默认关**——第三方 server 需要自己的凭据时用 `MCP_SUBPROCESS_ENV_EXTRA_KEYS`
   逐个加名，而不是退回继承整个环境；
5. **日志凭据脱敏**（§24.2 G4）：httpx 的异常文本会原样带出请求 URL，而 SerpAPI 的
   密钥就在 query string 里。`tools/adapters/search.py::redact_secrets` 对
   query / header / `Bearer` 三类形态把值打成 `***`、保留键名（便于定位是哪个参数配错）；
6. **设置接口的密钥只写不读**（§24.2 G9）：`*_api_key` / `*_secret` / `*_token` 后缀的
   字段在 `GET` 前掩码（保留末 4 位供辨认"配的是哪个 key"），`PUT` 拒收掩码回写
   （否则前端把 `***abc1` 原样提交会把真 key 覆盖掉），未知键 422；
7. **SQL 日志出口可控**（§24.2 G11）：`DB_ECHO` 独立开关。留空时沿用旧的 `bool(DEBUG)`
   推断，而 `DEBUG` 出厂为 `True` ⇒ 默认配置下 `engine.echo is True`，完整 SQL
   **连参数**经标准库 logging 落盘，绕过 loguru 出口与上面的脱敏纪律。
8. **错误路径不回显连接串凭据**（§24.2 G12）：`kb_ingest` 的 `connection_url` 里带着
   数据库密码，闸门（`KB_MYSQL_URL_GUARD`）拒绝时 detail 只写"哪个主机被拒"，
   绝不回放输入。这条不是理论担心：初版把校验写成 pydantic `field_validator`，
   实测 FastAPI 的 422 响应体把被拒的整条 URL（含密码）放进了 `errors()[].input`，
   **闸门自己成了凭据回显器**。口径与反向钉子见
   `docs/architecture/运行时护栏.md` §15.5、`tests/test_p108_kb_mysql_url_guard.py`。
   另外 `describe_for_log()` 只保留 scheme/用户/主机/库名，密码永不进日志。
9. **错误路径不回显过滤条件的值**（§24.3 T1 ⑫ 第二半）：同一条导入接口的 `filters` 里可能
   带着业务上敏感的值（工号、身份证号、内部编号），`sql_filters.build_where` 的报错只写
   "第几个条件违反了哪条规则"，被拒的**列名与值都不进消息**——错误路径才是泄露的高发地，
   上面那条 422 的教训对这条同样成立。探针用例见
   `tests/test_p113_where_parametrization.py::test_error_messages_do_not_echo_the_value`。

## 过渡改进（低成本，立即执行项）

1. `.env` 权限收紧：`chmod 600 .env`（Windows 侧限制到当前用户可读）；
2. `.env` 不进 Git（确认 `.gitignore` 覆盖）；示例只进 `.env.example`（无真实密钥）；
3. compose 迁移 `secrets:` 挂载（swarm/compose v2 语法），避免 `docker inspect` 泄露环境变量——见 `docker-compose.yml` 后续 PR；
4. 日志任何密钥值不进日志（现有约定：只打"explicit/temporary"状态）；
5. **硬失败面含 staging**：`resolved_secret_key` 与 `validate_app_settings` 的拒绝启动
   分支都按 `prod`/`production`/`staging` 判定（`STRICT_VALIDATION`），
   而不是只看 `PRODUCTION`——显式声明 `APP_ENV=staging` 的部署若只判生产，
   这道 fail-fast 会静默降级成"只打日志"。口径见
   `docs/architecture/运行时护栏.md` §15.4，回归测试在
   `tests/test_p107_sandbox_hardening.py`。

## 密钥轮换流程（SECRET_KEY / JWT）

1. 新密钥写入 `.env` 的 `SECRET_KEY_NEW`，应用支持双读（当前未支持则跳到快速路径）；
2. **快速路径**（当前实现）：停机窗口内换 `SECRET_KEY` → 重启。代价：所有已签发 JWT 失效，用户重新登录；
3. 验证：登录 → 刷新页面（新 cookie 有效）→ `/readiness` 正常；
4. 更新 `docs/runbooks/故障复盘模板.md` 记录轮换时间与影响面。

## API_KEY（服务间鉴权）轮换

1. 生成新 key → 调用方灰度切换 → 移除旧 key；
2. 中间件按常量比对（`APIKeyMiddleware`），暂不支持多 key 并存——轮换需协调调用方，切换窗口 < 1 分钟。

## 正式方案（立项前置条件）

- 密钥数量 > 10 或多环境部署成为常态时，接 **Vault / AWS Secrets Manager**；
- 选型约束：贴合现有 compose 部署形态（Sidecar 或 env 注入均可），不引入 K8S 依赖。
