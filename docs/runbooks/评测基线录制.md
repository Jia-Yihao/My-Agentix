## 八步录制流程（PowerShell）

### 第 1 步：启动基础设施

容器视角的完整栈（Linux / WSL 上）：

```powershell
docker compose up -d postgres redis neo4j mysql milvus kb_ingest
```

Windows 宿主机上按本机已有的容器起即可（本项目用
`my-agentix-redis-1` / `my-agentix-mysql-1` / `my-agentix-neo4j-local`），
Milvus 与 kb_ingest 可以不起——后果见第 6 步的 degraded 口径。

```powershell
docker ps --format "{{.Names}}`t{{.Status}}`t{{.Ports}}"
```

### 第 2 步：确认录制档环境（不再手敲环境变量）

录制档由 `--local-llm` 装配（本体 `evals/recording_env.py`），优先级
**进程环境 > `.env.local`（git 忽略） > 录制档默认**，`.env` 只在
「值里没有 compose 内网名」时被采纳。为什么不能让 `.env` 直接赢：
`.env` 是容器视角写的——`DATABASE_URL` 指向 `postgres:5432`、`NEO4J_URI` 指向
`neo4j:7687`、`LLM_BASE_URL` 指向远端 API，这些在宿主机上要么解析不到、
要么违反「模型一律本地」。

先看装配结果（不写盘、不请求，纯打印且脱敏）：

```powershell
$env:PYTHONIOENCODING = "utf-8"
.\.venv\Scripts\python.exe -c "import sys; sys.path.insert(0,'evals'); `
  from recording_env import build_local_recording_env; `
  print('\n'.join(build_local_recording_env()[2]))"
```

需要机器私有的值（模型 id、Neo4j 口令、非默认端口）就写进 `.env.local`，
不要改 `.env`，也不要改产品默认。

### 第 3 步：先录 4 条烟雾样本

一次全量录制是 60–90 分钟；先用一小撮金标把链路跑通，比事后考古便宜得多。
`--local-llm` 会在真正提问前做**录制前自检**（端点模型是否存在、KB 行数、
Neo4j 节点数、`articles` 数、Redis ping、kb_ingest 可达性），不齐直接退出码 2：

```powershell
.\.venv\Scripts\python.exe evals/run_eval.py --record --local-llm `
  --golden .tmp\smoke_golden.jsonl --predictions .tmp\smoke_predictions.jsonl `
  --results-dir .tmp\smoke_results
```

看三件事：`route=` 是否是预期路由、`src=` 是否 > 0（有源才谈得上引用命中）、
`status=` 是 `ok` 还是 `degraded`。

### 第 4 步：在线录制 102 条 golden 的预测

```powershell

```

### 第 5 步：提交基线预测文件

```powershell
git add evals/baseline_predictions.jsonl
git commit -m "evals: record baseline predictions (P0-1)"
```

### 第 6 步：离线复打分（与 CI 同款路径）

```powershell
.\.venv\Scripts\python.exe evals/run_eval.py --offline
```

读第 5 步提交的预测文件重新打分。**录制时已知限制**（务必连同数字一起读，
否则会把机位差异误读成质量差异）：

* KB 子图两条本地通道里 `postgres` 是 HTTP POST 到 kb_ingest（后端 Milvus
  `legal` 集合）。本机未起 Milvus/kb_ingest ⇒ 该通道每条失败 ⇒ 子图
  「通道失败 ≠ 查不到」，走本地 FAISS 兜底并打 `status=degraded`；
  路由只选 `milvus` 时则是 `ok`。打分口径**容忍** degraded
  （`score_reject`：「单纯的 `degraded` 不算误拒」），所以这是**口径内**的状态。
* `INGEST_SERVICE_URL` 在 `.env` 里是 `localhost:8000`，而本机 8000 属于
  **另一个项目**的服务（实测 `/openapi.json` 报 TicketPilot，其 `/api/search`
  只会 404）。录制档把它换成 compose 推导的 kb_ingest 端口（默认 8100）：
  宁可连接拒绝，不要跨项目串台。

### 第 7 步：生成 quality.json（不再逐个「首跑建档」）

```powershell
# 先看不写
.\.venv\Scripts\python.exe evals/write_quality_baseline.py `
  --summary evals/results\<stamp>.summary.json --dry-run
# 确认无误后写入
.\.venv\Scripts\python.exe evals/write_quality_baseline.py `
  --summary evals/results\<stamp>.summary.json
```

**为什么不用 `quality_gate.py` 的首跑建档来生成基线**（本 runbook 的旧版本就是这么写的）：

1. 建档路径的语义是 **NOT-ARMED / NOT-ENFORCED（没把关）**，用它「武装」门禁读起来像
   已经把关了；生成器把「建档」与「比对」两种语义分开。
2. 更硬的一条：**值为 `0.0` 的键一律不归档**。`*_applicable` 指标在「本轮没有适用
   样本」时是 `0.0`，而录制未跑完时可评测样本会全落在缺预测区间——2026-10-25 实测
   一份 17/102 的 summary 里，分母 34 的 `citation_correctness_applicable` 与分母 13
   的 `reject_accuracy_applicable` 都是 `0.0`。逐个建档会把 `0.0` 写成基线，于是这两个
   指标**恒 PASS**（`0.0 ≥ 0.0 × 0.98`）。`write_quality_baseline.py` 对这类键
   **拒绝写入**并把原因留在 `_meta.skipped_metrics`。这条闸 `--force` 也越不过（有单测钉住）。
   2026-10-26 起它的后果变重了：那个键不在基线里 ⇒ 门禁是 **NOT-ARMED（退出码 2，CI 红）**，
   不再是"响亮地没把关但仍绿"。所以一份残缺 summary 现在**归档不出可提交的基线**，
   要么补录、要么把该指标从 `ci.yml` 的 `METRICS` 里显式摘掉（见第 8.5 步的连带后果）。
3. 生成器还会在 `missing_prediction_count > 0`（录制未跑完）时拒绝建档，
   并在 `_meta` 里留下来源 summary、题数与各指标分母，使基线可核对。

### 第 8 步：门禁双向取证 + 提交

同值必须走**真比对 PASS**（而不是建档），劣化 5 个百分点必须 FAIL——
单向的绿不能证明门禁在把关。取证值取自 `evals/baselines/quality.json`（生成物，别手抄进别处）：

```powershell
.\.venv\Scripts\python.exe evals/quality_gate.py --baseline-file evals/baselines/quality.json `
  --metric route_accuracy --current 0.6275 `
  --max-regression 0.02      # 期望 PASS，且输出里没有 NOT-ARMED / NOT-ENFORCED
.\.venv\Scripts\python.exe evals/quality_gate.py --baseline-file evals/baselines/quality.json `
  --metric route_accuracy --current 0.5775 `
  --max-regression 0.02      # 期望 FAIL，退出码 1
```

实际结果（2026-10-25 首次、2026-10-26 对着门禁新默认值复跑，两次一致）：五个指标同值逐个
`verdict=PASS`、输出里两种"未武装"字样都没有、整体 exit 0；注入 −5pp 后五个全部
`verdict=FAIL`、整体 exit 1。

**为什么必须双向**：只跑同值那一次，看到的绿有可能是「根本没比对」。这条在 2026-10-25
真案发过：拿一份 17/102 的残缺 summary 对空基线逐个建档，五个指标全绿、exit 0，而被写进基线的是
`route_accuracy=0.1176`、`citation_correctness_applicable=0.0`、`reject_accuracy_applicable=0.0`——
后两个键从此恒 PASS（`0.0 ≥ 0.0 × 0.98`），门禁成了装饰。
两道闸分别堵掉那次的两种失效：`write_quality_baseline.py` 的「值为 0.0 不归档」
（`--force` 也越不过，`tests/test_p124_quality_baseline.py` 钉住），和门禁侧的
「缺键 ⇒ NOT-ARMED + 退出码 2 + 不改写基线文件」（2026-10-26 起，见第 8.5 步）。
今天的 FAIL 那一半还顺带证明**阈值不是地板本身**：若比对逻辑退化成恒 PASS，同值 PASS 看不出来，
−5pp 照样绿。

```powershell
git add evals/baselines/quality.json
git commit -m "evals: enforce quality gate baselines (P0-1)"
git push
```

推送后在 GitHub Actions 确认 `eval-offline` job 从「警告 + 跳过」升级为
「真跑分 + 逐指标门禁」；此后指标相对回退超过 2% 时该 job exit 1 阻断合并。
`tests/test_p124_quality_baseline.py` 里有一条
`test_committed_baseline_is_a_real_gate_not_an_empty_archive` 钉住这件事：
committed 的 `quality.json` 不再是 `{}`，且每个键都能被门禁真比对。

## 第 8.5 步：防「删一键 / 删输入 / 放宽预算」的静默降级

第 8 步的双向取证只覆盖**键都在**的情况。门禁最省事的降级不是改代码，而是
**从基线里删一个键**：旧口径下 `quality_gate.py` 对缺键的处理是
NOT-ENFORCED + 把本轮值**写回去建档** + 退出码 0——那一轮不比对，下一轮起本轮值就是新地板。
2026-10-25 独立审查按这句话复现过（在副本上做的，committed 文件未动）：

```powershell
# 这是**旧口径**的行为记录（2026-10-25），现在同样的命令会硬失败，见下。
Copy-Item evals/baselines/quality.json .tmp/dropkey.json
# （手工删掉 citation_correctness_applicable 那一行）
.\.venv\Scripts\python.exe evals/quality_gate.py --baseline-file .tmp/dropkey.json `
  --metric citation_correctness_applicable --current 0.5833
# 旧：NOT-ENFORCED + rc=0 + 那个键被写回副本
# 现：::error + NOT-ARMED + rc=2，副本逐位不变
```

2026-10-26 把上面这段在新口径下重跑了一遍（副本路径 `.tmp/dropkey.json`，用完即删）：
`rc = 2`，输出 `::error title=quality-gate::基线 … 中没有指标 citation_correctness_applicable
⇒ 该键未被把关，拒绝放行且不改动基线`，副本 sha256 前后同为 `cf82238b65663979…`、
那个键**没有**被写回来。旧日志里"rc=0 且键回来了"这两件事，现在每一件事都反过来。

### 口径变更（2026-10-26）：缺输入从「建档放行」改为「响亮阻断」

`evals/quality_gate.py` 现在有四态，其中三种都是"没真在把关"，标签各不相同：

| 态 | 触发 | 退出码 | 写基线文件 |
|---|---|---|---|
| `PASS` / `FAIL` | 键在、真比对 | 0 / **1** | 否 |
| `NOT-ARMED` | 基线文件不存在**或**缺该键，且没显式要建档（**默认**） | `NOT_ARMED_EXIT_CODE = 2` | **否** |
| `NOT-ENFORCED` | 同上缺失，但调用方显式带 `--allow-bootstrap` | 0 | 是（写当前值） |
| `SKIPPED` | 连当前值都没有（上游没出 summary） | 由 workflow 侧声明 | — |

三条设计理由，都是撞过现实才这么写的：

1. **2 ≠ 1**：1 的意思是"指标劣化了"，而 NOT-ARMED 什么都没比对。合成一个码，
   日志里就分不开"质量退步"与"没人把关"——后者的处置动作完全不同。
2. **拒绝路径上不写文件**：CI 悄悄改写一个 committed 的基线文件，比它不把关更难发现；
   而且"删掉基线里的一个键"本来是**最省事的放宽方式**（改代码要走评审，删一行 JSON 不用）。
   由 `test_missing_key_blocks_and_leaves_the_committed_baseline_untouched` 逐字节钉住。
3. **建档没有第三种中间态**：只有 `--allow-bootstrap` 显式声明才走旧语义。`ci.yml` 的
   `eval-offline` **不带**这一行；只有 `perf-baseline.yml` 的 nightly 带——那里"缓存被清 ⇒
   本轮无基线"是常态，每次都硬失败是噪声而不是信号。这条由
   `test_workflow_bootstrap_posture_is_explicit_where_it_is_needed` 守：以后谁把默认值翻回去，
   不会顺手把 nightly 打成一堆假红。

**连带后果（读基线生成器时要知道）**：生成器"值为 0.0 的键不归档"过去只是让那个键
响亮地没把关，现在它会**让 CI 红**——五键缺一，`eval-offline` 直接 NOT-ARMED。
可评审的处置只有两条：补录一份五键都能归档的 summary，或把该指标从 `ci.yml` 的
`METRICS` 里显式摘掉（后者会在 workflow 上留下一行改动，正是希望看到的形状）。

### 现在的钉子

pytest 侧（`tests/test_p124_quality_baseline.py` 15 条 + `tests/test_ci_gate_contract.py` 28 条）：

1. `test_committed_baseline_covers_every_ci_gate_metric` —— committed 基线必须**覆盖**
   ci.yml `METRICS` 的每个键，且生成器的 `CI_GATE_METRICS` 与之双向相等（键清单复用
   `test_ci_gate_contract._ci_gate_metrics` 从 ci.yml 现抽，不在测试里再抄一份清单，
   否则「两处各写一份判据迟早只关一条」）。
2. `test_committed_baseline_is_a_real_gate_not_an_empty_archive` —— 基线值下界收严为
   **开区间** `0.0 < value ≤ 1.0`（`0.0` 基线恒 PASS；原先的 `0.0 ≤` 会放行一份手改的常绿档）。
3. `test_ci_pins_the_regression_budget_instead_of_inheriting_the_default` —— 从 ci.yml 的门禁
   段落**正则抽出** `--max-regression` 的字符串值并断言 `== 0.02`。过去那里不传这个旗标，
   容差全在 `quality_gate.py` 的 argparse 默认值，而既有用例全部自己显式传值 ⇒ 往 ci.yml 加一行
   `--max-regression 0.99` 就静默解除全部五个指标的门禁、本地与 CI 都不红。
4. `test_committed_predictions_cover_the_golden_set_exactly` —— 门禁的**第二个输入**
   `evals/baseline_predictions.jsonl` 的内容守卫：存在 · 非空 · 题数与金标**同源**（与
   `legal_golden.jsonl` 行数相等，不写死 102）· id 唯一 · id 集合与金标双向相等。
   为什么不是"路径存在性"就够：预测文件缺失时 CI 走「响亮跳过」，job 依旧绿而门禁关着；
   而"文件在、被换成短档"连路径守卫都拦不住——它改写的是**分母**，比删文件更隐蔽。
5. 生成器侧同源闸：0.0 判定用 **`round(…, 4)` 之后的落盘值**，不是原始浮点——
   `0.00004` 折成 `0.0` 同样造出一盏永绿灯（当前分母 102/61/46/34/13 够不到，属潜在形态），
   由 `test_generator_does_not_archive_a_value_that_rounds_to_zero` 钉住。

**这道防线到底拦在哪（措辞曾被纠正过两次，别再照旧说）**：原先写「删键的提交在 CI 的 `test`
