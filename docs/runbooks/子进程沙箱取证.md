# Runbook：subprocess 沙箱档（⑮）的 Linux 取证

> 状态：**已执行**（2026-10-25，`python:3.12-slim` → Python 3.12.15，root 与
> `--user 1000:1000` 各一轮）。本 runbook 描述**可复现步骤 + 判据 + 当轮真输出**。
> 纪律与 `docs/runbooks/性能与成本采数.md` 一致：数字必须实测、标注测量环境；
> 测不到就写测不到，不编造。测试总数的真源在 README §11，本文只写"这两条文件在
> Linux 上跑到什么"，不复述全量数字。

## 为什么需要一份「换台机器跑」的 runbook

⑯ 的判据是**能力探测**而不是二进制探测（`agentix/tools/sandbox.py::probe_subprocess_caps`）：
Windows 上没有 `resource.setrlimit`、也没有进程组 kill，于是 `subprocess` 档在**执行点**
抛 `SandboxUnavailable`——一次 handler 都不调、一个子进程都不起（fail-closed，绝不静默
退回进程内）。这条口径的直接后果是：

`tests/test_p125_subprocess_sandbox.py` 里那组"资源闸真的落下了吗 / uid 真的降了吗 /
取消真的杀掉进程组了吗 / 墙里 `sys.modules` 干净吗"的用例，**在 Windows 上必然是
`skip`**。skip 是诚实的，但 skip 不等于验证——只有 Linux 才答得出这些问题。所以每一版
⑮ 的实现都要有一轮 Linux 真跑，而且 **root 与非 root 各一轮**：`uid` 降权这件事只有两种
结局（降成功 / 响亮拒绝），跑一次只能看见一种。

CI（`.github/workflows/ci.yml`，ubuntu-latest + Python 3.10）已经把 POSIX 组变成常驻真跑，
所以"忘了在 Linux 验"会先红在 CI。这份 runbook 服务的是另一种时刻：**CI 之外，我要当场
亲眼看见某一条证据**（比如评审质疑某个数字、或换了台机器想确认墙还在）。

## 第 1 步：起容器

```bash
docker run -d --name p125_linux \
  -v D:/code/my-agentix:/repo \
  python:3.12-slim sleep 5400
```

两个刻意的写法：

- **不要用 `docker run -w /repo`**：Windows 宿主上会把宿主路径带进 `-w` 校验，报
  `working directory 'D:/Git/Git/repo' is invalid`。统一用 `bash -lc 'cd /repo && …'`。
- **`sleep 5400` 而不是 `pytest …`**：容器留着，root 与非 root 两轮共用同一个镜像层，
  第二轮不必重装依赖（见第 3 步）。

## 第 3 步：跑 POSIX 组（root 与非 root 各一轮）

**先做字节码卫生，再谈跑**（不是可选的"清理一下"，是这一轮证据属不属于当前源码的前提）：

```bash
# 把树里任何先前编译的字节码清掉，保证 Linux 这次是从 .py 现场编译的
docker exec p125_linux bash -lc 'find /repo/agentix /repo/tests /repo/scripts /repo/evals \
  /repo/kb_ingest -name __pycache__ -prune -exec rm -rf {} + ; \
  find /repo/agentix /repo/tests -name "*.pyc" -delete; \
  find /repo/agentix /repo/tests -name __pycache__ | wc -l'
```

看到末行是 `0` 再继续。**路径刻意逐个列出来、不写 `find /repo`**：那会顺手把宿主
`.venv` 里的字节码也删掉——不影响正确性（会自动重编），但属于"取证改了工作树里不该改的东西"。
**为什么这一步在这份 runbook 里是硬性的**：CPython 校验 `.pyc`
是否过期用的是源文件的 **(mtime, size)**，而 Windows 宿主上编出来的 `__pycache__` 经
bind-mount 或 `cp -a`（**保留 mtime 与 size**）进容器后，这两个字段完全对得上 ⇒
容器里的解释器会**直接复用宿主编的字节码**，那句 `PYTHONDONTWRITEBYTECODE=1` 只挡"写"、
不挡"读"。后果不是"慢一点"：这一档的证据是"源码里的闸在真进程里落下了"，而复用旧字节码
时**跑的可能不是刚改过的那版源码**——取证与变异反证都会因此失真。
（2026-10-25 第 3 轮独立审查登记的现形方式：首轮 `-rs` 的 traceback 里出现的是
`D:\code\...` 路径。加本步后同两轮计数不变 ⇒ 那批结论没被污染，但**流程必须写下来**，
否则下一次改的是承重逻辑就没人能自证清白。不想删的话，用等价的第二方案：所有命令统一
`python -X pycache_prefix=/tmp/pyc -m pytest …`，读写都挪到容器本机。）

```bash
# root 轮（容器默认就是 root：`docker exec p125_linux id` 应当是 uid=0）
docker exec p125_linux bash -lc 'cd /repo && PYTHONDONTWRITEBYTECODE=1 \
  python -m pytest tests/test_p125_subprocess_sandbox.py tests/test_p114_execution_sandbox.py \
  -q -rs -p no:cacheprovider'

# 非 root 轮（同一个容器换用户；uid 降权的另一半结局只有这里才看得见）
docker exec --user 1000:1000 p125_linux bash -lc 'cd /repo && PYTHONDONTWRITEBYTECODE=1 \
  python -m pytest tests/test_p125_subprocess_sandbox.py tests/test_p114_execution_sandbox.py \
  -q -rs -p no:cacheprovider'
```

三个参数都不是装饰性的：

- `-p no:cacheprovider` 不写 `.pytest_cache`——非 root 用户对 bind-mount 里的 root
  产物未必有写权，缓存写失败会伪装成"测试环境坏了"。
- `PYTHONDONTWRITEBYTECODE=1` 不往 bind-mount 的仓库里撒 `__pycache__`（那会落进
  Windows 工作树）。
- `-rs` 打印跳过原因。**读跳过原因比读通过数重要**：Linux 轮只剩 2 条才是对的，且两条都
  在说"这台机器是 POSIX，所以那条 **Windows** 拒绝路径在这里测不出"（`skipif` 反过来写的
  那两个用例）。反过来，如果 Linux 轮里出现理由为
  `资源闸/setuid/进程组 kill 要本机探测通过才谈得上` 的 skip，那是 `probe_subprocess_caps()`
  把这台机器判成了"落不下资源闸"（或 `resource` 导不出来）——**墙自己的故障**，正是本 runbook
  要抓的东西。

当轮真输出（**2026-10-26 ⑰ 子集「进程数闸」落地之后复跑**，root 与非 root 两轮**第一次不逐位一致**，
而且这正是对的：进程数闸的取证腿要"能降权到独立 uid"，非 root 容器降不下去，于是两条 root-only
用例从"跑"变成"响亮地跳过"（skip 理由自己点名了该看哪条 else 分支）。这两轮**做了第 3 步的字节码
卫生**（先删仓库里的 `__pycache__`，再带 `PYTHONDONTWRITEBYTECODE=1` 跑）——上一轮"故意不清"是为了
复验 S1 修的是身份源而不是运气，那个目的已经达成并记在下面；本次要引用的是"跑的是当前源码"这句话，
所以卫生必须做回来）：

它从**本次真实采集**的 `session.items`（就是产出终端那行"N passed / M skipped"的同一份清单）
现算本文件条数，再核所有写这个短语的文档。为什么要有它：套件总数有守卫，**单文件条数没有**，
所以本文件 2026-10-25～26 这几轮里从 68 涨到 74、再涨到 78、80、93，README / CHANGELOG / runbook / PROJECT_SPEC /
ADR 里的手抄数字同时腐烂，而全量回归**一个字都没红**——这正是约定 7 说的"抄本当基准"。
现在加一条用例忘了改文档，那条守卫就红。（采集被 `-k` / nodeid / `--lf` / `--deselect` 缩窄时它

审查的 N1——漏了它，一次局部复跑会把"人为缩窄"报成"文档腐烂"。⚠️ 反过来，`--ignore` 掉本文件时
这条守卫**根本不会执行**，那是真空而不是绿，所以读日志要先看 `collected` 那行。）

**这条守卫自己的身份源也是第 4 轮审查点出来的（S1，严重）**：它原先用
`item.location[0]` 认"这条用例属不属于本文件"，而 `location` 来自 code object 的
`co_filename`——那是**编译时**写进 `.pyc` 的路径。于是第 3 步没做字节码卫生的那一轮里，容器复用了
宿主 Windows 编的字节码，同一个用例的两份身份分家（采集侧 `/repo/tests/…`、`co_filename`
`D:\Code\…\tests\…`），而 **POSIX 上反斜杠不是路径分隔符** ⇒ `Path(...).name` 把整条 Windows
字符串当成文件名 ⇒ 本文件被数成 0 条，守卫红在取证流程上、不是红在它该核的文档上。**修法是把身份源
换成采集侧的 `item.nodeid`**（pytest 用 `/` 拼、相对 rootdir，两平台同形），并加一条
`test_the_case_count_identity_source_survives_a_stale_pyc` 直接喂"nodeid 是 POSIX 相对路径、
location 是 Windows 绝对路径"的假采集项——**不需要真陈旧 `.pyc` 也能复现案发形态**。
复验证据（2026-10-26 第 4 轮那两腿，**故意不清字节码**）：root 与非 root 两轮各 **146 通过 / 2 跳过**，
且 `-rs` 的 skip 行打印的就是 `D:\Code\My-Agentix\tests\test_p125_subprocess_sandbox.py`
——那行 Windows 路径正是"容器确实在复用宿主字节码"的现场留痕，而计数不再受影响。

⚠️ **污染是双向的，而且墙自己会把它带回来**（2026-10-26 ⑰ 子集那轮现场撞见）：同一批
`.pyc` 后来出现在 **Windows 工作树**里，`co_filename` 是 `/repo/tests/…`——即容器编译的字节码
躺在宿主树上，宿主那一轮的 `-rs` 于是打印 `\repo\tests\…`。根因不是"忘了做卫生"：`scrub_env`
的 `OS_ENV_ALLOWLIST`（`agentix/domain/tool/exec_env.py`）**不含 `PYTHONDONTWRITEBYTECODE`**，
所以父进程导了这个变量、**墙里的子进程却导不到**。实测形状很干净地证明了这一点：清过
`__pycache__` 再带 `PYTHONDONTWRITEBYTECODE=1` 跑 root 轮，跑完仓库里只剩**两个** pyc——
`tests/__pycache__/subprocess_probe_handlers.cpython-312.pyc` 与
`agentix/tools/__pycache__/subprocess_worker.cpython-312.pyc`，`co_filename` 都是 `/repo/…`；
**父进程自己 import 的模块一个都没落盘**（`test_p125`／`test_p114` 的 pyc 不存在），落盘的全是
**子进程**按 `module`+`qualname` 重建时 import 的那两个。后果与 S1 同源但方向相反：Windows 侧的
`(mtime, size)` 校验对得上（同一份源文件），于是"这一轮跑的是宿主源码"这句话不成立。
**读法**：判定本身不受影响（守卫用 nodeid、`skip` 判据用探测真值，两处都不读 `co_filename`），
受影响的只有"源码新鲜度"这类断言的可信度——所以清 `__pycache__` 之后**必须马上跑**，且**每轮之前
都清**（本次跑完那两颗又长回来了），别在一轮里同时声称"清过"和"跑过墙"。（把该变量加进白名单是
行为变更，约定 5 未点头，本批没做。）

对照：**同一份文件在 Windows 宿主（同日）是「通过 71 条 / 跳过 22 条」**，22 条 skip 的理由
逐条都是 `资源闸/setuid/进程组 kill 要本机探测通过才谈得上`——那个 skip 数就是本文存在的理由。
Windows 侧的拒绝口径由 `test_non_posix_refuses_without_calling_handler`
等用例守着（它们跨平台都能跑，因为断言的是"什么都不做"）。

**skip 谓词必须与执行点的判定同源**（约定 6 ④）：判据取 `probe_subprocess_caps()["runnable"]`
而不是 `os.name == "posix"`。后者在"是 POSIX、但解释器没有 `resource` 扩展"的机器上会把
这 22 条从"响亮地跳过"变成"各自失败"——失败会被误读成代码缺陷，而真因是那台机器兑现不了
这一档承诺的隔离维度。`tests/test_p125_subprocess_sandbox.py::test_skip_predicate_is_the_probe_itself_not_a_second_guess`
把"判据 = 探测真值"这条关系钉住。

### 第 3.5 步：p131（code exec 机制）的两轮取证 + 变异反证

第 3 步验的是 subprocess 档本身。**code exec 机制**复用同一面墙（它的用例在
`tests/test_p131_code_exec.py`），但它多了一条此前无人看守的承诺——「墙被杀 ⇒ 孙进程随之被杀」
——所以要在这台容器上单独跑一轮。

**容器里要多装几个包**（第 2 步那套最小依赖不够，p131 会 import 到）。下面是当轮容器上
**实际执行过**的命令——`langchain-core==0.3.86` 是**前一步单独装的**，后一步装的是
`langchain-openai` 与 `langgraph` 那一族：

```bash
# ① langchain-openai（langchain-core 那一步在此之前已单独装好）
docker exec p125_linux bash -lc 'cd /repo && pip install --no-cache-dir \
  "langchain-openai==0.2.14"'

# ② langgraph 一族：prebuilt 与 checkpoint 必须一并写进去
docker exec p125_linux bash -lc 'cd /repo && pip install --no-cache-dir \
  "langgraph==0.2.60" "langgraph-prebuilt>=0.2.0" "langgraph-checkpoint==2.0.26"'
```

版本按仓内 `requirements.txt` 钉版补装（`requirements.txt:18-20` 钉 `langchain-openai==0.2.14`
与 `langchain-core>=0.3.85,<0.4.0`、`requirements.txt:32-33` 钉 `langgraph==0.2.60` 与
`langgraph-checkpoint==2.0.26`、`requirements.txt:94` 钉 `langgraph-prebuilt>=0.2.0`）。
**为什么把 `langgraph-prebuilt` 与 `langgraph-checkpoint` 一并写进去**：读者照抄这条命令
必须能一次跑通——只装 `langgraph` 而不带这两个，`import langgraph` 会因为缺 prebuilt/checkpoint
而报一个与"沙箱坏了"**无关**的错，而缺包报出来的错**长得像"沙箱起不来"**。
**但有两条传递依赖与仓内钉版对不上**：`tiktoken` 与 `regex`
是 pip 为 `openai` 传递解析出来的版本（`0.14.0` / `2026.9.29`），仓内钉的是 `0.13.0` / `2026.7.19`
⇒ 引用这一轮的读数时要连这个差一起说，否则换台机器复现不上。

**字节码卫生照旧**（第 3 步那套 `find … -name __pycache__ | wc -l` = **0** 之后再跑）：

```bash
# root 轮（容器默认 uid=0）
docker exec p125_linux bash -lc 'cd /repo && PYTHONDONTWRITEBYTECODE=1 \
  python -m pytest tests/test_p131_code_exec.py -q -rs -p no:cacheprovider'

# 非 root 轮（同一个容器换用户）
docker exec --user 1000:1000 p125_linux bash -lc 'cd /repo && PYTHONDONTWRITEBYTECODE=1 \
```

#### 变异反证：把承诺拆掉，让守卫变红

### 第 4.5 步：协议 v2 的归属凭证（墙内代码自己印一条"成功信封"）

前四步证的是"墙挡住了什么"，这一步证的是**"墙里的话不能冒充墙外的结果"**。

墙内代码有 stdout 写权限，而信封就写在 stdout 上：一句
`print("@@AGENTIX_SANDBOX@@ " + '{"ok": true, ...}')` 在旧口径（"取最后一条哨兵"）下
**就是一个成功结果**。协议 v2 因此给每次调用配一个归属凭证：父进程现生成
`nonce = secrets.token_hex(16)` 写进请求，**成功信封必须回显它**，父进程只认带本次
nonce 的那条；另有一条不对称规则：**退出码非 0 时 stdout 上的信封一律不采信**（worker
写出信封的分支都 `return 0`，rc≠0 意味着它根本没写完协议）。

探针 handler 在仓里（`tests/subprocess_probe_handlers.py::forged_success`，它打印一条
**没有 nonce** 的伪造信封后立刻 `os._exit`，让 worker 来不及写自己那条真信封），
重放脚本同样不进仓库（取证工具，不是被测物）。保存为 `/tmp/p125_forgery_replay.py`：

```python
import asyncio, json, sys
from agentix.tools.sandbox import SubprocessSandbox, SubprocessSandboxError
from tests.subprocess_probe_handlers import forged_success

async def main() -> int:
    wall = SubprocessSandbox()
    try:
        result = await wall.run(forged_success, {"tool_name": "echo"})
    except SubprocessSandboxError as exc:
        print("OK SubprocessSandboxError:", exc)
        return 0
    print("BAD forged result accepted:", json.dumps(result, ensure_ascii=False))
    return 1

sys.exit(asyncio.run(main()))
```


**反证（把规则改回去，旧口径立刻复现）**：在容器副本里把父进程那条筛选从
`e.get("ok") is True and e.get("nonce") == nonce` 改回 `or`、并把 `if rc != 0:` 改成
`if False:`，同一脚本的输出变成：


这一条是本 runbook 里唯一"必须能变红"的取证：它证明墙的那条规则不是文档里的漂亮话，
而是**墙里代码绕不过去的闸**。改完副本记得 `docker cp` 回真树再跑一遍（否则下一次
取证读到的是被改坏的墙）。

### 第 4.6 步：先印伪造件、再被打死（rc≠0 的那一条）

同一个探针还能扮演更凶的形态：`forged_success` 打完伪造件后以退出码 137 结束
（模拟被 `RLIMIT_CPU` 打成 SIGKILL）。此时 stdout 上有哨兵行、但 rc≠0——旧口径
（`rc != 0 and SENTINEL not in stdout`）会**采信**那条伪造件并把真正的失败原因
（进程崩了）盖掉。新口径下父进程直接拒：

```text

```

对应用例：`tests/test_p125_subprocess_sandbox.py::test_forged_envelope_plus_a_crash_is_still_not_a_result`。

### 第 4.7 步：伪造件里的 `ok` 不是布尔（协议 v2 补的第二道）

前两步验的是"伪造件**没有**归属凭证"和"进程崩了"。这条验的是**另一种**绕过：
墙内代码印一条**带着正确形态、但 `ok` 不是布尔**的信封——例如 `"ok": 1`。

为什么这是个洞：解析器若把 `ok` 不是 `True` 的信封归进"失败桶"，而父进程的终局判定用
**真值**（`not envelope.get("ok")`），那么 `not 1` 是 False ⇒ 这条伪造件被当**成功结果**
返回。**归属凭证在这一路上压根没执行过**——nonce 校验再严也拦不住一个"从来没进过
trusted 桶"的值。（2026-10-25 第 2 轮独立审查点名的严重项。）

现在的口径是**严格布尔**：`ok` 只认 `True` / `False`；`1` / `1.0` / `"true"` / 缺失一律
按**畸形信封**拒，**刻意不归拢进失败桶**。worker 自己只写布尔值（`ok: True` / `ok: False`），
所以非布尔的信封只可能是墙内代码印的。终局那一行也改成 `is not True`——这是**解析器之外的
第二道闸**，两层各自独立：只改回其中一层，伪造件仍被拒。

同一个探针换个 `ok` 取值即可扮演这个形态（`forged_success` 的 `args["ok_value"]`），
重放脚本不进仓库，保存为 `/tmp/p125_forgery_replay3.py`。它一次跑**五条**路径——
「`ok=True` 但不带 nonce」（归属凭证那道）、「`ok=1`」「`ok=1.0`」「`ok="true"`」「`ok=null`」
（严格布尔那道；`null` 是第 3 轮审查登记的一般项 G1 补的，另有"整个 `ok` 键不存在"那一形态
只在纯函数侧钉，因为探针写不出"缺键"的信封）：

```python
import asyncio, json, sys
from agentix.tools.sandbox import SubprocessSandbox, SubprocessSandboxError
from tests.subprocess_probe_handlers import forged_success

async def _one(label, args, expect_substr):
    wall = SubprocessSandbox()
    try:
        result = await wall.run(forged_success, args)
    except SubprocessSandboxError as exc:
        text = str(exc)
        ok = expect_substr in text
        print(f"[{'PASS' if ok else 'FAIL'}] {label}: rejected with {text[:160]!r}")
        return 0 if ok else 1
    print(f"[FAIL] {label}: forged result ACCEPTED: {json.dumps(result, ensure_ascii=False)}")
    return 1

async def main() -> int:
    bad = 0
    bad += await _one("ok=True / no nonce", {"tool_name": "echo"}, "untrusted success envelope")
    bad += await _one("ok=1 / non-boolean", {"tool_name": "echo", "ok_value": 1}, "malformed response envelope")
    bad += await _one("ok=1.0 / non-boolean", {"tool_name": "echo", "ok_value": 1.0}, "malformed response envelope")
    bad += await _one("ok='true' / non-boolean", {"tool_name": "echo", "ok_value": "true"}, "malformed response envelope")
    bad += await _one("ok=null / non-boolean", {"tool_name": "echo", "ok_value": None}, "malformed response envelope")
    print("REPLAY_RESULT:", "ALL_GOOD" if bad == 0 else f"{bad}_BAD")
    return bad

sys.exit(asyncio.run(main()))
```

⚠️ 这条脚本把**拒因**也算进 PASS/Fail（`expect_substr`），不是只看"有没有泄漏数据"。
这不是吹毛求疵：只改回失败桶那一层时，五条非布尔伪造件**仍然全被拒**，但拒因从
`malformed response envelope` 退化成 `[unknown] no error given`——数据没漏，诊断瞎了。
所以那一轮的退出码是 4 而不是 0，**读数时必须分清"被当成成功"和"被拒但理由不对"**。

当轮真输出（`python /tmp/p125_forgery_replay3.py`，退出码 0 = 五条都按预期理由被拒）：

### 第 4.8 步：进程数闸的两本账（任务 vs 进程）

前七步验的是"墙立不立得住"。这一步验墙里**唯一带前置条件**的那道闸
`RLIMIT_NPROC`——它不是"写了就生效"，有三个特性，每一个单独都能把"我验过了"
变成假象：

1. **计费单位是任务**：线程也占额度，不是"进程数"。
2. **uid 0 被内核豁免**（`CAP_SYS_RESOURCE`）：`setrlimit` 照样成功、回读照样是那个数，
   但一次都不拦。"调过 `setrlimit`" ≠ "闸生效"。
3. **按整机 uid 记账，不认 PID 命名空间**：容器 `/proc` 数出来的只是**下限**。

取证脚本 `.tmp/nproc_tasks_evidence.py`（不进仓库，容器里跑；root 起，实验本体先
`setuid` 到专用 uid 60000）：

```bash
MSYS_NO_PATHCONV=1 docker cp .tmp/nproc_tasks_evidence.py p125_linux:/tmp/nproc_tasks_evidence.py
docker exec p125_linux bash -lc 'python /tmp/nproc_tasks_evidence.py' > .tmp/nproc_evidence_20261026.log 2>&1
```

`MSYS_NO_PATHCONV=1` 不是可选项：Git Bash 会把 `/tmp/...` 改写成 Windows 临时目录，
于是 `docker cp` 把文件放进宿主机、`docker exec` 又去宿主机路径里找（报
`can't open file '//C:/Users/.../nproc_tasks_evidence.py'`）。

脚本做两件事：

- `experiment(cap, threads_first)`：降权 → 写 soft=cap → 先起 `threads_first` 个线程
  → 再 fork 到 `EAGAIN`。`forks_started` 就是这道闸实际给的预算。
- `measure_threaded_process(n)`：同一 uid 下**一个进程**起 n 个线程，回读两本账
  （与任何 rlimit 无关，单独回答"线程到底算不算"）。

本次真输出（2026-10-26，`p125_linux` / `python:3.12-slim` / 3.12.15，uid 60000；
完整日志 `.tmp/nproc_evidence_20261026.log`）：

| cap | 预起线程 | 落闸时任务数 | fork 成功 | 落闸时进程数 |
|---|---|---|---|---|
| 8 | 0 | 1 | **7** | 1 |
| 8 | 4 | 5 | **3** | 1 |
| 8 | 7 | 8 | **0**（第 0 次就 EAGAIN） | 1 |
| 16 | 10 | 11 | **5** | 1 |

两条读法：

1. `fork 成功 = cap − 落闸时任务数`，四行逐项对得上（8−1=7、8−5=3、8−8=0、16−11=5）。
   "落闸时任务数"就是子进程自己加 1（它也是一个任务）加上预起的线程数。
2. **落闸时进程数始终是 1**。如果余量检查读的是进程数，它会报"还剩 7 个坑"，而墙里
   第 0 次 fork 就 `EAGAIN`——观测面全绿、业务全红，这是最难归因的形态。同一 uid 的
   两本账（`measure_threaded_process`）：

```text
{"threaded_process": {"requested_threads": 0, "processes": 1, "tasks": 1, "max_threads_of_one_process": 1}}
{"threaded_process": {"requested_threads": 5, "processes": 1, "tasks": 6, "max_threads_of_one_process": 6}}
```

⇒ 一个进程、5 个线程 = **进程 1 / 任务 6**。两个数字不可互换。

> 读输出时注意一个探针自身的产物：`experiment` 的子进程 `fork` 之后会继承父进程**尚未
> 刷出的 stdout 缓冲**，`os._exit` 前那次 `flush` 会把父进程之前打过的行再打一遍，于是
> 日志里出现重复块。只认 `CHILD_JSON` 开头的那四行（外加 `threaded_process` 两行），
> 不要把重复块的次数当成实验次数。

**uid 0 豁免**（`.tmp/nproc_root_exempt.py`，同一容器、root 直跑）：

```text
{"euid": 0, "uid": 0, "soft_before": -1, "soft_written": 5, "soft_read_back": 5,
 "forks_succeeded": 12, "fork_blocked_errno": null, "blocked_is_eagain": false}
```

soft 写 5、回读 5、随后连起 **12** 个进程一次不阻塞。所以 `nproc_gate_plan` 对
`uid=0` 的判定是"**不落**"——包括运维显式配 `TOOL_SANDBOX_SUBPROCESS_UID=0` 的情形：
落一道只对别人生效的闸，比明说"这道闸没落"更危险（`applies=true` 会让读数的人以为
fork 炸弹已经被钉住）。

**`/proc` 只是下限**（同一个探针，`SANDBOX_EVIDENCE_UID=65534`）：

```text
{"uid": 65534, "processes": 0, "tasks": 0, "max_threads_of_one_process": 0}
CHILD_JSON {"cap": 8, "threads_first": 0, "uid": 65534, ..., "forks_started": 0, "fork_blocked_is_eagain": true}
CHILD_JSON {"cap": 8, "threads_first": 4, "uid": 65534, ..., "threads_started": 0,
            "thread_errors": ["RuntimeError: can't start new thread"], ..., "forks_started": 0}
```

`/proc` 数到 **0 个进程 / 0 个任务**，soft=8 下第 0 次 fork 就 `EAGAIN`，连起线程都被
拒（线程同样计费）。原因是内核那份计数跨整机：同宿主机上别的容器/进程以这个 uid 跑着
东西，它们不在这个 PID 命名空间的 `/proc` 里。⇒ 文档里说"专用 uid"时，**专用是相对
整个内核**，不是相对这个容器；`no_headroom=false` 也不保证 fork 成功，它只说明"这个
命名空间里没看见占满"。

墙里的落点（读代码时对照这四处）：

- `subprocess_worker.apply_gates`：**降权之后**才谈 nproc；`limits.payload["nproc"]` 取自
  `sandbox.RLIMIT_NPROC = 32`（任务数）；落闸前用 `_scan_uid_ledgers` **同一次扫描**读
  两本账（分开读会得到两个时刻的快照，比错的还难查）。
- `nproc_gate_plan(...)` 返回固定 6 键 `applies / cap / uid_process_count / uid_task_count /
  no_headroom / reason`，是全仓唯一判点：`cap<=0`、`uid<0`（共用父 uid，计数含整个登录
  会话）、`uid=0`（内核豁免）三条不落；`applies` **不依赖** `/proc` 可不可读，否则同一个
  配置在两台机器上会得到两种结论。
- `probe_subprocess_caps()`：父进程用**同一份** `nproc_gate_plan` 给 `nproc_gate`
  （计数留 `None`——探测结论不许随 `/proc` 可读性漂移），且这一项**不进 `missing`**：
  "没配独立 uid"从来不在这一档的承诺里，混进 `missing` 会让"开了 flag 但没配 uid"的
  机器整档被拒，那是行为变更而不是加固。
- 未落时 `caps.nproc_gate.applies=false` 照常回传，父进程 `_log_caps` 对同一条 `reason`
  **只告警一次**，不阻断调用（约定 2）。看到 `subprocess sandbox dimension not enforced:
  RLIMIT_NPROC stayed off because ...` 不是故障，是墙在如实报"这道闸今天没落"。

⚠️ **这个实验唯一的致命坑：残留任务会把下一轮预算静默清零。** `RLIMIT_NPROC` 按整个
uid 计费，上一个实验留下的僵尸/孙进程哪怕只剩一个，下一轮读出来就是"这道闸每次都立刻
咬死"。所以探针每轮先 `drain()`：轮询到该 uid 一个任务都不剩才继续（本次
`clean_after_s: 0.0`）；fork 出来的孙进程由子进程自己 `waitpid` 收回——容器里 PID 1
通常不 reap，孤儿僵尸会**永久**占着这个 uid 的额度。这一条是量出来的，不是推的。
换了新容器或换 uid 复跑时，先跑一次 `report_counts()` 看该 uid 是不是 0，再信后面的数。

对应用例：

- 判定/探测/告警侧（Windows 上也真跑）：`::test_the_process_count_gate_declines_while_the_uid_is_shared`、
  `::test_the_process_count_gate_applies_under_a_dedicated_uid_and_reports_headroom`
  （两本账取较大值、`no_headroom`、`/proc` 不可读时"未知"而非 (0,0)）、
  `::test_the_process_count_gate_declines_for_uid_zero_because_root_is_exempt`、

  同源）、`::test_a_missing_process_gate_is_warned_about_once` /
  `::test_an_applied_process_gate_is_not_warned_about`（告警只响一次、真落了就不响）、

  `::test_the_process_count_gate_bites_once_the_uid_is_dedicated`、

- **`python:3.12-slim` 没有 procps**：`ps` 不存在，直接 `FileNotFoundError`。孤儿进程检测
  因此读 `/proc/<pid>/cmdline`（`tests/test_p125_subprocess_sandbox.py::_live_worker_processes`
  按此实现，`ps` 只是 fallback）。换镜像时若 `/proc` 被挂得不可读，那条用例会**误报"没有孤儿"**，
  先确认 `cat /proc/self/cmdline` 有输出。
- **Windows 宿主上 `subprocess.run(text=True)` 按 cp936 解码**：矩阵生成器打印中文，管道
  线程里抛 `UnicodeDecodeError`，而 pytest 把它吞成 warning ⇒ 断言照样读不到内容。所有
  跨进程读输出的地方都得显式 `encoding="utf-8", errors="replace"`（已按此写死）。
- **别在资源闸的进程内跑 `apply_gates`**：`cpu_s=7` 会把正在跑的 pytest 自己被 SIGXCPU 打死。
  所以闸的验证一律**在子进程里**（`_apply_gates_in_child` 起一个 `python -c` 的孩子），软限
  只会收紧不会放宽，测不到就如实回报。
- **Windows 编的 `__pycache__` 会在 Linux 里"看起来是新的"**：`.pyc` 的过期判定只看源文件
  的 `(mtime, size)`，而 bind-mount 与 `cp -a` 都保留这两项 ⇒ 容器直接复用宿主编的字节码，
  `PYTHONDONTWRITEBYTECODE=1` 拦得住写、拦不住读。所以第 3 步把"清字节码"写在跑之前，
  且**每次变异/还原后都要再清一次**（变异只改一两行时最容易撞上"跑的还是旧字节码"）。
  另一条等价做法是全命令统一 `python -X pycache_prefix=/tmp/pyc`，读写都落在容器本机。
- **容器里 `.env` 会跟着 bind-mount 进来**：`Settings` 的 `env_file=".env"` 按 cwd 解析，
  所以 `cd /repo` 那一步会读宿主 `.env`（会看到 `KB_RERANK_SCORE_THRESHOLD is deprecated…`
  这类告警，属正常）。这不影响沙箱证据——**子进程的环境是白名单裁出来的，不是继承来的**。
- **不要在 Windows 上跑 POSIX 组然后"当它过了"**：本次 Windows 结果是"通过若干 + POSIX 组
  skip"，那两个 skip 必须靠本文的第 3 步补上，而不是靠 `--no-header -q` 少看两行。
- **p131 在容器里还额外需要 `langchain-core` / `langchain-openai` / `langgraph` 一族**（按 `requirements.txt` 钉版补装：
  `langchain-core==0.3.86` / `langchain-openai==0.2.14` / `langgraph==0.2.60` +
  `langgraph-prebuilt>=0.2.0` / `langgraph-checkpoint==2.0.26`——**实际执行过的命令见第 3.5 步**）——第 2 步那套
  最小依赖装完直接跑 p131 会缺包，而缺包报出来的错**长得像"沙箱起不来"**。
  **两条传递依赖与仓内钉版有差**：`tiktoken` / `regex` 是 pip 为 `openai` 传递解析出来的版本
  （`0.14.0` / `2026.9.29`），仓内钉的是 `0.13.0` / `2026.7.19` ⇒ 引用这一轮的读数时
  要连这个差一起说。
- **带 `PYTHONDONTWRITEBYTECODE=1` 跑完，仓库里仍会长回两颗 `.pyc`**：
  `agentix/tools/__pycache__/subprocess_worker.cpython-312.pyc` 与
  `tests/__pycache__/subprocess_probe_handlers.cpython-312.pyc`——落盘的都是**子进程**按
  `module`+`qualname` 重建 handler 时 import 的模块，父 pytest 自己 import 的一个都没落盘。
  根因与第 3 步记的那条同源：`scrub_env` 的环境白名单**不含** `PYTHONDONTWRITEBYTECODE`
  （加它属行为变更，约定 5 未点头，本批没做）⇒ 父进程导了、子进程导不到。
  **所以收尾要再清一次**，别在一轮里同时声称"清过"和"跑过墙"。

## 本 runbook 不声称的部分

- ⑮ **没有买到**：只读根文件系统、指定可写目录、出网默认拒绝。这三件一起属 ⑰/T3。
  ⑰ 规划四件里的**进程数闸 `RLIMIT_NPROC` 已买到，但它是唯一带前置的一道**：它只在
  `TOOL_SANDBOX_SUBPROCESS_UID` 配了**独立且非 0** 的 uid 时落下，且挡的是"这个 uid 能起多少
  **任务**"（线程也算任务），不挡"往哪儿连、读哪个文件"。所以口径仍是"**是墙，不是笼子**"——handler 崩了、把内存吃了、把密钥
  读了都出不了进程，但它 `open()` 一个 world-readable 文件、或往外连一个 socket，这一档不管。
- 默认档仍是 `in_process`；**没有任何既有工具被改成走墙里**。`EXECUTION_SANDBOX_ENABLED`
  与 `TOOL_SANDBOX_SUBPROCESS_ENABLED` 都默认关，且 staging override **没有**钉开档位
  （矩阵由 `python scripts/gen_staging_matrix.py --check` 校，见
  `docs/runbooks/预发环境与配置矩阵.md`）。
- 证据全部来自 **`python:3.12-slim` 容器 + Windows 宿主 + 本地 LM Studio 环境**，
  **不是**生产/staging 集群；CI 的 3.10 常驻真跑是另一条独立的兜底。
- **`PR_SET_PDEATHSIG` 这一条只在 Linux 成立**：口径 §5 已写明"macOS 没有 `prctl`"⇒ 非 Linux
  平台上**那条承诺是不成立**，不是"没测"。Windows 上那条行为用例恒 skip 是**按设计**
  （skip 判据取自执行点**同源**的能力探测 `parent_death_signal_supported()`，不是另写的平台判断）。
  本文的 Linux 两轮只证明"在 Linux 上落得下"，**不外推**到其它平台。
